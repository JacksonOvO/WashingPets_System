## 零、这份文档是干嘛的

这是一台 **宠物智能洗护设备（洗狗机）** 的 **主控固件**，跑在 **STM32F407** 芯片上。

它和 ESP32 那个 LED 项目最本质的区别是：

| | ESP32 LED 项目 | 这个洗宠机项目 |
|---|---|---|
| 芯片 | ESP32-S3（乐鑫） | STM32F407（意法半导体） |
| 系统 | ESP-IDF（自带 RTOS） | STM32CubeMX + FreeRTOS + HAL |
| 连网方式 | WiFi / MQTT / 云 | RS232（连电脑）+ RS485（连设备） |
| 控制对象 | 1 颗 LED | 几十个阀门/泵/风机/加热棒/传感器 |
| 复杂度 | 入门级 | 工业级（安全互锁、多任务、在线升级） |

一句话概括：**这台机器的核心就是「读一堆传感器 → 判断该干什么 → 控制一堆执行器」，而且必须保证安全（宠物在里面，急停、门锁、温度都不能出错）。**

这份文档讲的是 `WashingPets_App` 这个工程（应用固件）。旁边还有个 `WashingPets_Bootloader`（引导程序，负责给 App 在线升级），本文末尾会提一句它的作用，但重点在 App。

## 一、这个项目是什么（成品长什么样）

### 1.1 设备本体

一台洗狗机，把狗放进舱里，自动完成「冲水 → 打沐浴液 → 揉搓/浸润 → 冲干净 → 吹干 → 放出来」，结束后还能**自动清洗机器自己**。

设备由这些子系统组成：

1. **舱门机构**：上门电磁锁、下门电磁锁、上门闭门器（自动关门）、上下光幕（检测有没有东西挡门）、门磁到位开关。*现在没有电动推杆，靠闭门器自动关门。*
2. **水路系统**：水箱、自来水阀、热水器阀、旁通阀（内循环加热）、冷热水比例调节阀（混合出水温度）、增压泵（加压）、4 个淋浴阀（上/中/下/后）、4 个自清洁阀、各种药液阀（沐浴液/芬香/柔顺/除螨/消毒/护毛素）。
3. **烘干系统**：左/右/底部 3 个风机、左/右/底部 3 个加热棒、顶部排风扇。
4. **环境系统**：舱外温湿度、舱内温湿度、氧气、臭氧、四路水温采集。
5. **自清洁系统**：顶部、左侧上层、左侧夹层、后端 4 个清洁位置。
6. **其它**：可控硅（调电压）、蠕动泵（精确输液）、紫外线灯、臭氧、照明、主板电源。

### 1.2 软件长什么样

- 上电后进入 **自动模式空闲层**（不会自己乱动）。
- 电脑上的「调试工作台」通过 **串口（RS232）** 下发命令：
  - 切换自动/手动模式
  - 启动完整自动流程 / 单独测某一段
  - 下发/修改 26 套「配方」（针对不同犬种、体型、毛长）
  - 实时看状态、看曲线、控制单个 IO、触发 OTA 升级
- 完整自动流程是一条「**入舱准备 → 入舱 → 洗前准备 → 冲洗 → 沐浴 → 清洗 → 吹干 → 出舱准备 → 出舱 → 自清洁**」的流水线。
- 流程中设备会不断向电脑上报「我当前在第几步、传感器值是多少、有没有故障」。

### 1.3 代码量大概多少

`Core/Src` 里有 40+ 个 C 文件、约 1.5 万行。最大的几个：`app_iap.c`（上位机协议 + 升级，57KB）、`task_comm485.c`（485 通信，35KB）、`task_output.c`（输出仲裁，25KB）、`task_water_tank.c`（水箱，25KB）。

## 二、新手必懂概念（逐词讲清）

如果你从没碰过单片机，先把这几个词搞懂，后面看代码会轻松很多。

### 2.1 单片机 / MCU

单片机 = 一块芯片里塞进了一台「只能跑一个固定程序的小电脑」。上电就从 `main()` 开始执行，断电停止。它没有操作系统界面，就是死循环 + 中断 + 定时器。

### 2.2 STM32F407

意法半导体（ST）出的 32 位单片机，内核是 ARM Cortex-M4：

- 主频 168MHz
- 1MB Flash（存程序，掉电不丢）+ 192KB RAM（存变量，掉电丢）
- 一堆外设：GPIO（引脚高低电平）、USART（串口）、TIM（定时器）、ADC 等

### 2.3 HAL 库 与 STM32CubeMX

- 直接操作单片机寄存器很痛苦（要记几百个地址）。ST 提供了 **HAL 库**（硬件抽象层），把「配置串口」「读一个引脚」封装成函数：`HAL_UART_Init()`、`HAL_GPIO_WritePin()`。
- **STM32CubeMX** 是 ST 官方图形化工具：点一点选外设，它自动生成初始化代码和工程骨架。这个工程的 `APP.ioc` 就是 CubeMX 的配置文件，`main.c` 里的 `MX_USART1_UART_Init()`、`MX_GPIO_Init()` 都是它生成的。

> 代码里凡是 `/* USER CODE BEGIN ... */ ... /* USER CODE END ... */` 夹着的，是你（人）自己写的代码；外面的是 CubeMX 生成、每次重新生成会覆盖的。所以自己写代码要写进 USER CODE 区，否则改配置会丢。

### 2.4 FreeRTOS / 任务 / 队列 / 事件标志

单片机默认是「一条路走到黑」的单线程。但如果既要读串口、又要控制水泵、又要上报状态，单线程就会互相耽误（等一个慢动作时别的都停了）。

**FreeRTOS** 是一个轻量操作系统，让单片机「看起来同时做很多件事」。核心概念：

- **任务（task / thread）**：一个独立的执行流，有自己的 `for(;;)` 循环。比如「上位机通信任务」「485 通信任务」「自动流程任务」是三个并行任务。
- **调度器（scheduler）**：决定谁先跑谁后跑。高优先级任务能打断低优先级任务。
- **队列（queue）**：任务之间传数据。比如「485 任务」往队列里塞一条「把 14 号加热棒设成 80%」，消费方再取出来执行。
- **事件标志（event flags）**：任务之间传「信号」。比如「上位机任务」置一个 `CLEAN_EVENT_REQUEST` 标志，自清洁任务平时阻塞在 `osEventFlagsWait` 上，一看到标志就醒来干活。

这个项目用的是 **CMSIS-RTOS v2**（一套标准的 RTOS 接口），它底层还是 FreeRTOS。所以你会看到 `osThreadNew`、`osMessageQueuePut`、`osEventFlagsWait` 这种 `os` 开头函数。

### 2.5 RS232 与 RS485

都是**串口通信**（一帧一帧地收发字节）。

- **RS232**：点对点，连电脑。这个项目用它连「调试工作台」，波特率 115200。
- **RS485**：总线型，一条线上能挂几十个设备（一对多），差分信号，抗干扰强、能拉长距离。工业设备最爱用。这个项目用它连传感器和风机/加热棒/泵，波特率 9600。

关键区别：**RS485 是半双工、一主多从**——主机（STM32）一个个问，从站（传感器）被问到才回答，不能主动说话，否则撞车。

### 2.6 Modbus-RTU

跑在 RS485 上的**工业通信协议**，规定「怎么组织字节、怎么算校验、从站怎么回答」。核心规则：

- 每个从站有一个**站号**（1~247），主站发命令要带站号。
- 帧里有 **CRC16 校验**，收方算一遍对不上就丢弃。
- 主站发「写寄存器」命令，从站执行后回一个应答；主站发「读寄存器」命令，从站回数据。

这个项目里 RS485 上的传感器、风机、加热棒、增压泵、比例阀**全是 Modbus-RTU 从站**，STM32 是主站，轮流去「读传感器、写执行器」。

### 2.7 上位机 / 调试工作台

「上位机」= 跑在电脑上的软件，通过串口跟单片机通信，负责给人看、让人操作。这个项目的上位机是一个 **WPF 调试工作台**（Windows 程序，在 `Bootloader/tools/APP_IAP/` 下），能连串口、控制 IO、控制 485、下发配方、触发流程、记录曲线、执行 OTA 升级。

单片机 = 「下位机」，电脑 = 「上位机」。（一上一下，主机在下。）

### 2.8 Bootloader / IAP 在线升级

- 正常情况下，程序烧进芯片要插调试器（SWD/JTAG）。但设备装好了、放现场了，不可能每次升级都拆机插线。
- 办法：把 Flash 分成两段——前面放一个**引导程序（Bootloader）**，它很小，只干一件事：收到新固件，把它写进后面那段 Flash，然后跳过去运行。
- **IAP（In-Application Programming，在应用中编程）** = 程序运行时自己给自己刷固件。

这个项目的布局：

```
0x08000000 ────────────────────── Bootloader（16KB，开机先跑它）
0x08004000 ────────────────────── App（本工程，768KB，真正干活的程序）
0x080C0000 ────────────────────── 参数区（128KB，存 26 套配方等，升级时不动它）
```

所以 App 的 `app_iap.h` 里有 `APP_IAP_APP_ADDRESS 0x08004000`，`main.c` 里那句 `SCB->VTOR = FLASH_BASE + VECT_TAB_OFFSET` 就是把**中断向量表**搬到 App 的起始地址，让程序在 0x08004000 也能正常响应中断。

### 2.9 工艺流程 / 状态机

「给狗洗澡」不是一个动作，而是一串有先后、有条件、有超时的步骤。编程上把它组织成**状态机**：

- 有大状态（阶段）：入舱、冲洗、烘干……
- 每个阶段里又有小状态（步骤）：开阀、等水温、开泵、计时……
- 每一步有进入条件、执行动作、完成条件、失败处理。

这个项目的做法叫「**线程 + 阶段表 + 步骤表**」，下一章详细讲。

### 2.10 Flash 参数存储

程序里要「记住」的东西（比如 26 套配方、默认功率）必须存到 **Flash**（掉电不丢）。这个项目把参数统一放在 Flash 的 **Sector 10**（`0x080C0000`，128KB），并且：

- 开头写一个「魔术值」判断这块区域初始化过没有；
- 存一个版本号 + 长度 + CRC32 校验，防止结构升级或数据损坏；
- 升级 Bootloader/App 时**不要擦这个扇区**，配方就能跨升级保留。

### 3.2 三个最重要的设计思想

**① 流程和硬件隔开（auto_device 设备抽象）**

流程代码只说「打开淋浴阀上」，**不说**「把 PB12 拉低」。具体哪个引脚、高低电平是什么含义，全部集中在 `auto_device.c` 和 `task_output.c` 里。好处：换硬件接线，只改一处，流程代码不动。

**② 所有输出统一仲裁（task_output）**

为什么不让流程直接 `HAL_GPIO_WritePin()`？因为：

- 手动/自动要互锁（手动开了的，自动不能乱动，反过来也是）；
- 急停、门没关、光幕被挡这些**安全条件**要统一判断；
- 多个任务不能同时抢同一个输出点。

所以所有开关量输出都走 `TaskOutput_Request(来源, 点位, 开/关)`，由 `task_output` 统一判断「该不该真的开」。查输出问题只看这一个文件。

**③ 线程 + 阶段表 + 步骤表（app_flow）**

把复杂的自动流程拆成三层，越往下越通用：

```
task_auto.c        只负责周期性调用 AutoProcess_Process()（薄薄一层）
auto_process.c     管「大阶段」：现在在第几个阶段、这个阶段完了跳下一个
app_flow.c         通用执行器：给定一张「步骤表」，从头跑到尾
auto_stage_*.c     每个阶段各自的「步骤表」+ 每步的动作函数
```

这一套的好处是：**加一个新阶段 = 加一个 `auto_stage_xxx.c` + 在阶段表里登记一行**，不用动调度器的核心逻辑。

## 五、代码逐文件详解

下面按「从入口到细节」的顺序，逐个讲每个文件是干什么的、关键逻辑是什么。

### 5.1 `Core/Src/main.c` —— 程序入口

一切从这里开始。流程：

1. `HAL_Init()` → `SystemClock_Config()`（把主频配到 168MHz）
2. `MX_GPIO_Init()`、`AutoDevice_Init()`、`TaskOutput_InitHardware()`（把输出全部关到安全状态）
3. `MX_USART1_UART_Init()`（USART1，115200，连上位机）+ `MX_USART3_UART_Init()`（USART3，9600，连 RS485）
4. **`SCB->VTOR = FLASH_BASE + VECT_TAB_OFFSET;`** —— 把中断向量表重定位到 App 区（因为程序实际在 0x08004000 跑）
5. 发一句 `"APP START\r\n"` 给上位机，然后 `AppParam_Init()` 读参数
6. 启动 FreeRTOS：`osKernelInitialize()` → 创建默认任务 → `AppTasks_Create()` 创建所有业务任务 → `osKernelStart()`（调度器开始接管，之后 `main` 不再往下走）

还实现了几个辅助函数：

- `UART2_Send()` —— 给上位机发数据的接口。**注意：它名字叫 UART2，实际用的是 `huart1`（USART1）**，这是个遗留命名，容易误导（代码审查里也点了这个问题）。
- `HAL_UART_RxCpltCallback()` —— 串口收到一个字节就进中断，把字节塞进一个**环形缓冲区** `host232_rx_buffer`。环形缓冲区就是一个固定大小的数组，头尾两个指针，写满就覆盖最旧的。
- `UART2_Read()` —— 上位机通信任务从这个环形缓冲区取数据。
- `StartDefaultTask()` —— 一个「运行指示灯」任务：手动模式常亮，自动模式每 1 秒闪一下。

### 5.2 `Core/Src/app_tasks.c` —— 创建所有任务

`AppTasks_Create()` 里一口气创建了这些任务：

| 任务 | 创建函数 | 干什么 |
|------|----------|--------|
| 输出仲裁 | `TaskOutput_Create()` | 所有 GPIO 输出的统一出口 |
| 上位机通信 | `TaskHost232_Create()` | 解析命令、上报、IAP |
| 485 通信 | `TaskComm485_Create()` | RS485 总线排队收发 |
| 自动流程 | `TaskAuto_Create()` | 调度整个自动流程 |
| 自清洁 | `TaskClean_Create()` | 自动流程结束后触发 |
| 自检 | `TaskSelfTest_Create()` | 一键检测整机 |
| 水箱恒温 | `TaskWaterTank_Create()` | 后台维持水位水温 |
| 生命保障 | `TaskLifeSupport_Create()` | 氧气/温度安全保护（**当前被 `APP_ENABLE_LIFE_SUPPORT_PLACEHOLDER 0U` 关掉了**） |
| 看门狗 | `TaskWatchdog_Create()` | 喂狗 |

看到没，一个「任务」对应一个 `task_xxx.c` 文件，职责清清楚楚。这就是多任务架构的好处。

### 5.3 `Core/Src/app_flow.c` + `app_flow.h` —— 通用流程执行器（核心中的核心）

这是整个项目最值得吃透的文件，因为自动流程、自清洁、自检**全都复用它**。

#### 5.3.1 一个「步骤」长什么样

```c
struct AppFlowStep
{
  uint16_t id;                 /* 步骤编号 */
  const char *name;            /* 步骤名，比如 "SPRAY_VALVE_ON" */
  const char *description;     /* 动作说明，比如 "打开淋浴阀" */
  uint32_t delay_before_ms;    /* 动作前延时 */
  uint32_t delay_after_ms;     /* 动作后延时 */
  AppFlowAction action;        /* 动作函数，返回 RUNNING/DONE/FAIL/JUMP */
};
```

#### 5.3.2 每一步的执行顺序（一个小的状态机）

每个步骤内部有 3 个阶段：

```
DELAY_BEFORE（动作前延时）
   → ACTION（调用 action 函数）
   → DELAY_AFTER（动作后延时）
   → 下一步
```

- `action` 返回 `DONE`：这一步完成，进后延时，延时到了 `current_index++` 走下一步。
- `action` 返回 `RUNNING`：这一步还没完（比如在等水温达标），下一轮周期**再调用一次** action，继续等。
- `action` 返回 `FAIL`：立刻关所有危险输出，流程失败。
- `action` 返回 `JUMP`：跳到指定步骤（配合 `AppFlow_JumpToStep`）。

#### 5.3.3 最关键的一处：安全优先

`AppFlow_Process()` 每次被调用，**第一件事**是检查：

```c
if ((AutoDevice_IsEmergencyStopped() != 0U) ||
    (AutoDevice_IsStopRequested() != 0U))
{
  AutoDevice_AllDangerousOutputsOff();
  ctx->running = 0U;
  ctx->failed = 1U;
  return;
}
```

意思是：**不管是冲洗还是烘干，只要急停被按了、或者上位机让停止，立刻关掉所有危险输出并终止流程。** 这个检查放在通用执行器里，就覆盖了所有流程，不会漏。

> 新手常见误区：以为「流程要一步步走完」。其实这里的设计是「每一步都要被一个高频周期任务反复调用」，所以每一步都可以随时被打断、随时被安全检查拦下来。**不是阻塞式地一路跑到底，而是每 10ms 回来判断一次该干嘛。**

### 5.4 `auto_process.c` + `auto_process.h` —— 自动流程总调度

它管「大阶段」的跳转。阶段枚举：

```c
typedef enum
{
  AUTO_PROCESS_STAGE_ENTRY_ENV = 0,  /* 入舱准备 */
  AUTO_PROCESS_STAGE_ENTRY,          /* 入舱流程 */
  AUTO_PROCESS_STAGE_WASH_READY,     /* 洗前准备 */
  AUTO_PROCESS_STAGE_SPRAY,          /* 冲洗 */
  AUTO_PROCESS_STAGE_BATH,           /* 沐浴 */
  AUTO_PROCESS_STAGE_CLEAN,          /* 清洗 */
  AUTO_PROCESS_STAGE_DRY,            /* 吹干 */
  AUTO_PROCESS_STAGE_EXIT_PREPARE,   /* 出舱准备 */
  AUTO_PROCESS_STAGE_EXIT,           /* 出舱流程 */
  AUTO_PROCESS_STAGE_COUNT
} AutoProcessStage;
```

核心机制是**「请求 → 处理」解耦**：

- 上位机发 `启动完整流程`，实际只调 `AutoProcess_RequestFull()`，它只置一个标志 `full_request = 1`，**不立刻跑**。
- `task_auto` 周期调 `AutoProcess_Process()`，它发现标志置了，才真正 `AutoProcess_Start()` → `start_stage(0)`。

为什么要多此一举？因为**命令是从「上位机任务」进来的，但流程必须在「自动流程任务」这个单一上下文里跑**，否则两个任务同时改流程状态就乱套了。所有跨任务的「停止/启动/终止」都走这个模式：**请求方只置标志，属主任务在自己的循环里处理。**

`AutoProcess_Process()` 的周期逻辑：

```
AppFlow_Process(&auto_flow);       // 推进当前阶段（跑步骤表）
if (AppFlow_IsFinished) {
    if (单段测试模式) 停止;
    else if (还有下一阶段) current_stage++, start_stage(下一个);
    else 全部完成 → 触发自清洁 TaskClean_Request();
}
```

还提供了**单段测试**：`AutoProcess_RequestStageTest(AUTO_PROCESS_STAGE_DRY)` 可以只跑烘干这一段，跑完就停、不触发自清洁——现场调试单独某一段动作特别有用。

### 5.5 `auto_stages.h` + `auto_stage_*.c`（9 个文件）—— 各阶段步骤表

每个阶段一个文件，内容就是一张「步骤表」+ 每步的动作函数。例如冲洗阶段的表（在 `auto_stage_spray.c`）大致是：

```
STEP(1,  "确认门关闭、水温达标")
STEP(2,  "再次确认水温")
STEP(3,  "打开淋浴阀")
STEP(4,  "设置流量")
... 一直到最后 STEP(16, 冲洗完成上报)
```

`AUTO_STEP` 宏把它们拼成 `AppFlowStep`：

```c
#define AUTO_STEP(id, name, before, after, action_func, desc) \
  { (id), (name), (desc), (before), (after), (action_func) }
```

9 个阶段对应 9 个文件：

| 文件 | 阶段 |
|------|------|
| `auto_stage_entry_env.c` | 入舱准备（调温调湿到适合狗进舱） |
| `auto_stage_entry.c` | 入舱（开门 → 狗进 → 关门 → 锁门） |
| `auto_stage_wash_ready.c` | 洗前准备（等水温达标、请求上位机选配方） |
| `auto_stage_spray.c` | 冲洗 |
| `auto_stage_bath.c` | 沐浴（打沐浴液） |
| `auto_stage_clean.c` | 清洗（冲干净） |
| `auto_stage_dry.c` | 吹干 |
| `auto_stage_exit_prepare.c` | 出舱准备（降到和舱外差不多温度，避免狗一出门着凉） |
| `auto_stage_exit.c` | 出舱 |

`auto_stages.h` 里还集中定义了各阶段的**固定延时**（比如 `DRY_FAN_RAMP_TIME_MS 10000` 表示烘干风机 10 秒内从 50% 升到 100%），以及把配方时间 + 固定延时算成「总时间 / 剩余时间」的宏。**改延时只改这一个文件，上报给上位机的时间会自动跟着变。**

### 5.6 `task_clean.c` + `clean_process.c` —— 自清洁

和自动流程是同一套架构的「小型复用」：

- `task_clean.c`：一个线程，阻塞等待 `CLEAN_EVENT_REQUEST` 事件，收到就 `CleanProcess_Start()` + 循环 `CleanProcess_Process()`。
- `clean_process.c`：自清洁自己的步骤表 `self_clean_steps[]`（顶部、左侧上层、左侧夹层、后端 4 个位置 + 烘干）。

自动流程全部结束后，`auto_process` 会调 `TaskClean_Request()` 触发它（用 `clean_requested` 标志防止重复触发）。

### 5.7 `auto_device.c` + `auto_device.h` —— 设备抽象层

这是「流程代码」和「具体硬件」之间的隔离层。它定义了 4 个大枚举：

- `AutoInputPoint`（输入点）
- `AutoOutputPoint`（输出点）
- `AutoCommand`（上位机命令，如「开门」「继续」）
- `AutoFaultCode`（故障码，如 `AUTO_FAULT_EMERGENCY_STOP`、`AUTO_FAULT_TANK_TEMP_SENSOR_INVALID`）

关键接口：

- `AutoDevice_ReadInput(point)` —— 读输入（内部已经做了滤波：液位类要稳定 3 秒，门磁/光幕/急停去抖 30ms）。
- `AutoDevice_SetOutput(point, enabled)` —— 设置输出。
- `AutoDevice_AllDangerousOutputsOff()` —— 关所有危险输出（急停/故障时用）。
- `AutoDevice_SetCommand(cmd)` / `AutoDevice_ConsumeCommand(cmd)` —— 上位机交互的「请求/消费」对。
- `AutoDevice_SetFault(code)` / `AutoDevice_GetFault()` —— 故障的存取。

还有个重要开关：

```c
#define AUTO_DEVICE_HOST_COMMAND_BYPASS  0U
```

`1` = 开发调试阶段，不真等上位机，所有「开门」之类的命令都假装已收到；`0` = 联调阶段，必须等上位机真的回了命令流程才继续。**正式联调必须设成 0。**

### 5.8 `task_output.c` —— 输出仲裁

所有 GPIO 开关量的唯一出口。核心接口：

```c
HAL_StatusTypeDef TaskOutput_Request(AppOutputSource source,
                                     AutoOutputPoint point,
                                     uint8_t enabled);
```

- `source` 分 `APP_OUTPUT_SOURCE_AUTO`（自动）和 `APP_OUTPUT_SOURCE_MANUAL`（手动）。
- 内部维护一个「请求表」，把「谁想要这个点开/关」记下来，再根据**模式 + 安全互锁**算出「实际该不该开」，最后才写 GPIO。
- 手动/自动互锁：切换模式时 `TaskOutput_ClearSource()` 把另一方来源的请求清掉。

这是「输出不直接写 GPIO」这条规则的落地点。

### 5.9 `task_comm485.c` —— RS485/Modbus 通信

整个 RS485 总线只有这一个任务能碰（避免多任务抢总线）。它维护一个**命令队列**：

- 其它模块调 `TaskComm485_RequestSetPercent(站号, 百分比)` 把「控制命令」**入队**（不阻塞、不等结果）。
- 这个任务循环里**出队 → 发帧 → 等应答 → 记录成功计数**，同时还要轮流去「读 4 路传感器」。

关键设计：

- **成功计数** `TaskComm485_GetStationSuccessCount(station)`：每个从站记一个「成功收发次数」，自检就是靠「写命令后这个计数有没有 +1」来判断从站是否真的响应了。
- **抑制机制** `TaskComm485_InhibitNonzero(reasons)`：急停、安全停机、暂停、故障时可以「封禁一切非零输出命令」，防止危险执行器在故障状态下被打开。
- **每轮限量** `COMM485_MAX_COMMANDS_PER_LOOP = 4`：防止风机/加热棒频繁调功率把传感器轮询挤掉（这是历史上「传感器突然全变成 FF」的根因之一）。

### 5.10 `task_host232.c` + `app_iap.c` —— 上位机协议 + IAP

这是**最大的两个文件**，负责和电脑对话：

- `app_iap.c`：解析上位机发来的二进制帧（`0x55 0xAA` 开头 + CMD + SEQ + LEN + Payload + CRC16），分发到对应的业务命令；同时包含 **IAP 在线升级**的完整流程（接收固件分包 → 写 Flash → 校验 CRC32 → 重启）。
- `task_host232.c`：通信线程本体，从 `main.c` 的环形缓冲区取字节，喂给 `app_iap` 解析。

协议细节见第六章，IAP 的版本/地址定义在 `app_iap.h`：

```c
#define APP_IAP_APP_ADDRESS    0x08004000U  /* App 起始地址 */
#define APP_IAP_TARGET_ID      0x407A0C06U  /* 设备型号标识 */
#define APP_IAP_VERSION        0x00020301U  /* 软件版本 2.3.1 */
```

### 5.11 `app_param.c` + `app_param.h` —— 参数存储

- 定义了 `AppRecipe_t`（一套配方，68 字节，含水箱目标温度、各路水压、各阶段时间、自清洁时间等 22 个字段）。
- 定义了 `AppSelfTestConfig_t`（自检参数，40 字节，含保压阈值、加热观察时长等）。
- 整个 `AppParam_t` 存在 Flash Sector 10（`0x080C0000`），开头有魔术值 + 版本 + CRC32。
- 提供「读取 / 修改 RAM / 保存到 Flash」三层：修改只进 RAM（`SetRecipe`），显式 `SaveNow()` 才写 Flash。**上位机改参数后必须发 SAVE 命令，否则断电丢。**

### 5.12 `task_self_test.c` —— 自检

一键检测整机的流程，分**快速（12 项）**和**深度（18 项）**两种，详见第七章。

### 5.13 其它后台任务

- `task_water_tank.c`：水箱恒温后台线程——待机时维持水位/水温，自清洁前补水到高液位，用水阶段暂停让泵和阀。
- `task_life_support.c`：生命保障（氧气/温度/湿度安全），**当前是占位、未启用**。
- `task_watchdog.c`：看门狗喂狗。
- `oxygen_sensor.c` / `temperature_module.c` / `thyristor.c`：三个 Modbus 从站驱动（氧气、四路水温、可控硅），帧扫描 + CRC 逻辑大同小异。

## 六、上位机通信协议（精简版）

完整版见同目录的 `STM32_上位机通信协议说明书.md`（1900+ 行，非常全）。这里只讲「小白看懂原理需要的最小知识」。

### 6.1 一帧长什么样

```
+-------+-------+-----+-----+-------+-------+---------+-------+-------+
| HEAD1 | HEAD2 | CMD | SEQ | LEN_L | LEN_H | PAYLOAD | CRC_L | CRC_H |
| 0x55  | 0xAA  | 1B  | 1B  |  1B   |  1B   |  0..N   |  1B   |  1B   |
+-------+-------+-----+-----+-------+-------+---------+-------+-------+
```

- `HEAD1 HEAD2`：固定 `0x55 0xAA`，用来在字节流里找到「一帧的起点」。
- `CMD`：命令号。业务命令 `0x30~0x43`，主动上报 `0xA1~0xA7`，应答 `0xF0`(成功)/`0xF1`(失败)。
- `SEQ`：序号，请求和响应要一致，用来对得上「这条响应是回哪条请求的」。
- `LEN`：Payload 长度，**小端**（低字节在前）。
- `CRC16`：校验，算错了整帧丢弃。

### 6.2 命令速查

| CMD | 名称 | 方向 | 说明 |
|-----|------|------|------|
| 0x30 | QUERY_DEVICE_STATUS | 主机→设备 | 查状态 |
| 0x31 | SET_WORK_MODE | 主机→设备 | 切模式（空闲/手动/自动/维护/故障） |
| 0x32 | PROCESS_CONTROL | 主机→设备 | 启动/暂停/继续/停止/终止服务/单段测试/自清洁/清故障 |
| 0x33 | PROCESS_INTERACTION | 主机→设备 | 回复设备的「开门/关门/选配方」请求 |
| 0x40 | GET_PARAM_BLOCK | 主机→设备 | 读参数/配方 |
| 0x41 | SET_PARAM_BLOCK | 主机→设备 | 改参数（进 RAM） |
| 0x42 | SAVE_PARAMS | 主机→设备 | 保存到 Flash |
| 0xA1 | DEVICE_STATUS | 设备→主机 | 上报「在干嘛」 |
| 0xA3 | INTERACTION_REQUEST | 设备→主机 | 请求上位机操作（如开门） |
| 0xA4 | FAULT_EVENT | 设备→主机 | 上报故障 |
| 0xA5 | TELEMETRY | 设备→主机 | 周期上报传感器数据（500~1000ms 一帧） |

### 6.3 一个关键交互：开门

自动流程走到「入舱」时，需要开门。但门不能设备自己随便开，要等操作员确认：

1. 设备发 `0xA3 INTERACTION_REQUEST`（带一个自增的 `request_id`，类型 = 「打开上舱门」），**每 1 秒重发一次**直到有回复。
2. 上位机回 `0x33 PROCESS_INTERACTION`（带同样的 `request_id`，result=1 表示确认）。
3. 设备校验 `request_id` 匹配后，才执行开门动作。

为什么用 `request_id` 而不是简单置个标志？**防止「上一轮流程延迟到达的旧开门命令，被下一轮流程误用」**——这是实战踩出来的坑。

### 6.4 参数修改的完整流程

```
GET_PARAM_BLOCK（读）→ 用户改 → SET_PARAM_BLOCK（进 RAM，拿到新 revision）
→ SAVE_PARAMS(新 revision)（写 Flash）→ 再 GET 核对
```

`revision`（修订号）用来防止两个界面同时改参数互相覆盖。

## 七、自检系统

自检 = 正式洗护前对整机执行机构的一次自动化体检，跑在 `task_self_test.c` 里，全程就是一个阻塞式顺序流程（用 `osDelay(20ms)` 轮询）。

| 模式 | 项数 | 内容 |
|------|------|------|
| 快速 QUICK | 12 | 3 风机(通信) + 3 加热(通信) + 注水 + 4 淋浴阀(保压) |
| 深度 DEEP | 18 | 上面全部 + 3 加热(真的测升温) + 更多阀 + 热水回路 |

五个阶段：

- **A 风机 ×3**：写 50% 转速，看该站「成功计数」有没有 +1 → 判定通信正常。
- **B 加热 ×3**：快速模式只验证通信；深度模式要真把舱温加热 0.5℃ 才算通过（还会监控舱温不超 45℃）。
- **C 注水路径**：开自来水阀 + 比例阀，看水位能不能到中液位（超时 180 秒）。
- **D 阀门加压 ×N**：开被测阀 → 增压泵加压到 3.0bar → 看能不能**稳定保持 2 秒**在 [2.8, 3.2]bar 区间。
- **E 热水路径**（仅深度）：开热水阀，看水箱温度连续 3 次采样上升。

贯穿全程的安全守卫：急停、门没关、光幕被挡、舱温超限、液位矛盾，任何一条都立刻 `ABORT` 终止自检。

完整的判据和参数表见同目录的 `自检逻辑流程说明书.md`。

## 八、踩坑记录与已知问题

### 8.1 开发过程中遇到的（来自项目记忆文档）

- **传感器突然全变 `FF FF`**：根因是执行器命令把传感器轮询挤掉了。解决：限制每轮执行器命令数量（`COMM485_MAX_COMMANDS_PER_LOOP = 4`），先执行器后传感器。
- **自清洁「手动结束后又自动重跑」**：事件标志没清，被主流程下一拍重新判定成需要自清洁。解决：理清自清洁触发条件和结束标志。
- **右风机（11 号）控制不了**：站号不一致 / 旧站号清零逻辑干扰 / IO 页和 485 页控制路径不一致，逐个排查。
- **水箱明明到温度还加热**：先确认 CH2 温度采集真实、是否已收到配方，再排查是否被增压泵电气干扰（最后发现是电气干扰，不是代码）。
- **出舱「开上舱门」按钮无效**：入舱开门和出舱开门是两个不同的交互请求，request/stage/type 不能混用。
- **OTA 版本号对不上**：DMP 期望 `1.0.1`，实际返回 `0x02000000`，报 `VERSION_VERIFY_FAILED`。解决：统一版本编码规则（`major<<16 | minor<<8 | patch`）+ 小端序，APP 启动后主动上报 `RSP_APP_READY` 带正确的版本/大小/CRC。

### 8.2 代码审查发现的（安全相关优先，详见 `Docs/代码审查问题报告.md`）

这份 22 条的审查报告是**还没修完的活**，但非常值得读。摘最关键的几条：

1. **安全停止闩锁被水箱任务每秒解开**：`RequestSafeStop()` 是闩锁式保护（急停后封禁非零 485 输出），但水箱任务每个周期无条件调 `ReleaseSafeStop()`，导致故障后封锁最多撑 1 秒就被解开，加热棒/风机可能在故障状态下重新上电。→ 应改成只在「非自动→自动」切换沿释放一次。

2. **暂停→恢复后水路空跑**：暂停关了所有输出，恢复却只 `SetPaused(0)`，没有重新开水的步骤，也没有 `ReleaseSafeStop()`。结果恢复后淋浴阀不开、水空跑到计时结束。

3. **写参数时全系统冻结 1~2 秒**：F407 内部 Flash 单 bank，擦 128KB 的 Sector 10 要约 1 秒，期间 CPU 不能取指，**急停都停摆**。→ 保存要加门条件，流程运行中不允许擦 Flash。

4. **无独立看门狗**：`IWDG` 被注释、`HardFault_Handler` 是 `while(1)` 死循环。野指针崩溃时加热棒/风机会**冻结在最后状态**持续加热。→ 启用看门狗 + 崩溃处理里先把危险输出写成安全电平。

5. **485 急停最坏延迟数秒**：命令队列是阻塞式 `osMessageQueuePut`，掉线站点单条命令能阻塞约 2 秒，急停命令要排队。→ 排空循环每条后重查急停标志，响应超时从 500ms 压到 100ms。

6. **沐浴阶段开的可能是消毒液阀**（存疑，需对图纸）：代码里 `WaterPathOn` 开的是 `DISINFECTANT_VALVE`（消毒液阀），但液位检查查的是沐浴液、步骤描述写的是沐浴液阀。**要先对硬件图纸确认**。

7. **多处等待无超时**：等水位、等水温、等门锁都可能**永久挂死**，而对应的故障码早就定义了却没用上。

> 这些问题的共同根因，很多指向同一个设计要点：**在嵌入式里，「安全停机」这种关键路径不能依赖某个后台任务碰巧不捣乱，必须是显式的、边沿触发的、有超时兜底的。** 读这份报告比读任何教程都更能理解「工业级固件」和「能跑」之间的差距。

### 8.3 一个贯穿始终的教训

**硬件问题不要只从代码角度修。** 项目里多次出现「增压泵一开，温度采集就异常」，最后定性是**电气干扰**（电源地、屏蔽、终端电阻、模块供电），不是代码 bug。排查顺序应该是：先确认传感器数据真实、再查通信是否被挤占、最后才怀疑代码逻辑。

## 九、下一步 / 扩展方向

按「安全 → 功能 → 健壮性 → 体验」的顺序建议：

1. **先修 8.2 里的安全类问题**（问题 1~7）：尤其看门狗、急停延迟、暂停恢复、写参数冻结这几条，直接关系到「宠物在舱里是否安全」。
2. **补齐无超时的等待**：给所有 `while(等待条件)` 加超时 + 故障上报，避免流程挂死。
3. **485 掉线退避**：连续失败 N 次的从站跳过 M 轮，避免一个死站拖垮整条总线。
4. **参数版本迁移**：当前版本号一变，26 套配方全丢回默认。建议做保留式迁移。
5. **启用生命保障线程**：现在 `task_life_support` 是占位，氧气/温度/湿度安全保护还没真正生效，发布前必须接上。
6. **IAP 深审**：`app_iap.c` 的擦写边界、分包校验、状态机还没专项审查。

### 建议的阅读顺序

如果你是小白，想真正读懂这份代码：

1. 先读 **本文**（架构 + 概念）。
2. 再读 **`app_flow.c`**（流程执行器的状态机，最核心）。
3. 再读 **`auto_process.c`**（阶段跳转）和 **`auto_device.h`**（硬件抽象，全是注释）。
4. 然后挑一个阶段，比如 **`auto_stage_spray.c`**，对着 `自动流程运行说明.md` 看步骤表怎么跑。
5. 想懂通信就读 **`STM32_上位机通信协议说明书.md`**（协议）和 **`自检逻辑流程说明书.md`**（自检）。
6. 想懂「怎么做对」就读 **`Docs/代码审查问题报告.md`**（反面教材，收获最大）。
