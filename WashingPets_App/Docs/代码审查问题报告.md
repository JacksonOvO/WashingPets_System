# 一、严重问题

## 1. 安全停止闩锁被水箱任务每秒解除

- **位置**:`task_water_tank.c:592`
- **原因**:`TaskComm485_RequestSafeStop()` 的设计是闩锁式保护——急停/门故障/暂停时置 `nonzero_output_inhibited=1`,之后一切非零 485 输出(三路风机、三路加热、增压泵、比例阀)都被拒绝,只有流程切阶段、自清洁启动等正式路径才解除。但水箱任务在"自动模式+非急停"分支里**每个周期(约1秒)无条件调** `TaskComm485_ReleaseSafeStop()`。
- **后果**:任何触发 SafeStop 的故障发生后,485 封锁最多维持 1 秒就被水箱解开。如果此时烘干 Monitor 还在调温、清洗预热还在请求,加热棒/风机会在故障状态下重新上电。
- **复现**:自动流程进入烘干 → 断开上门到位信号模拟门故障 → 观察 485 加热棒:断开约 1 秒后,烘干的温控请求又被放行,加热重新上电。
- **解决**:改成边沿触发——记录上次的 `TaskOutput_IsAutoMode()`,只在"非自动→自动"的切换沿 Release 一次,其余时间不调用。

## 2. 暂停→恢复后水路空跑、485 恢复靠运气

- **位置**:暂停 `app_iap.c:964-966`;恢复 `app_iap.c:982-983`
- **原因**:暂停执行 `AllDangerousOutputsOff()`(撤 GPIO 输出 + 485 封锁),恢复却只 `SetPaused(0)`。两个问题:
  a) 冲洗/沐浴/清洗的"开水开阀"步骤早已 DONE,流程停在计时步骤,恢复后**没有任何步骤重新开水**;
  b) 恢复不调 `ReleaseSafeStop()`,正式路径上没有解除——实际上靠问题 1 里水箱任务每秒 Release 的副作用,1 秒后才解开;这一秒内烘干温控的 `set_heaters` 返回 `HAL_BUSY`,部分步骤(如 `FanTargetHeaterFullOn`)对非 OK 直接判 FAIL。
- **后果**:恢复后水阶段**无水空跑到计时结束**(宠物没洗成,沐浴液也没清水稀释);恢复点落在烘干/预热段时流程可能直接失败。
- **复现**:完整流程进冲洗(已开水)→ 上位机发暂停,等 2 秒发继续 → 观察淋浴阀不再打开,直到冲洗计时结束。烘干阶段同样操作 → 观察流程 FAIL 或温控停摆。
- **解决**:① 恢复分支补 `TaskComm485_ReleaseSafeStop()`;② 水路输出改为幂等——在 `CheckTime`/`Monitor` 这类 RUNNING 循环的步骤里每周期重发开水输出(`TaskOutput` 仲裁本身是幂等的,重发无副作用),这样暂停恢复后水路自动回来。

## 3. 沐浴阶段开水路开的是消毒液阀(存疑,需对图纸确认)

- **位置**:`auto_stage_bath.c:65`(`WaterPathOn`)、`:183`(`LiquidOff`)、`:31`(`stop_bath`)、`:53`(`CheckLiquid`)
- **原因**:`WaterPathOn` 打开的是 `AUTO_OUTPUT_DISINFECTANT_VALVE`(消毒液阀),但液位检查查的是 `BATH_LIQUID_LOW`(沐浴液低液位),`stop_bath` 关的是 `BATH_LIQUID_VALVE`,步骤描述写的是"打开…沐浴液阀"。**全文件没有任何地方打开过沐浴液阀**。
- **后果**(若确实接错):沐浴阶段加进喷淋水的是消毒液而非沐浴液——消毒液浓度/成分不是为接触动物皮肤设计的;且消毒液阀同时服务自清洁,两条管路功能混乱。
- **复现**:单段测试沐浴阶段,在 `WaterPathOn` 步骤看实际吸合的是哪个阀;或对照接线图确认该输出点物理接的阀。
- **解决**:确认图纸后:若开错,`:65` 和 `:183` 改为 `AUTO_OUTPUT_BATH_LIQUID_VALVE`;若硬件就是这根管,统一所有命名、注释和液位检查,消除歧义。

## 4. 写参数时全系统冻结 1~2 秒(含急停)

- **位置**:`app_param.c:235` `AppParam_SaveNow()`;触发点 `task_auto.c:120`(延迟保存)、`app_iap.c:1519`(SAVE_PARAMS 命令)
- **原因**:F407 内部 flash 是单 bank,擦除 128KB 的 Sector 10 典型约 1 秒(手册最大约 2 秒),擦写期间 CPU 无法从 flash 取指,**所有任务和中断全部冻结**。当前触发不检查机器是否在运行。
- **后果**:冻结期间急停输入、输出互锁复查、485 接收全部停摆,输出冻结在当前状态——如果正在喷淋/加热,就是 1~2 秒的安全盲区。
- **复现**:自动流程运行中,上位机修改任意配方(延迟保存约 1 秒后落盘)或直接发 SAVE_PARAMS → 观察遥测/输出停顿 1~2 秒。
- **解决**:保存加门条件——`AutoProcess_IsRunning()==0 && TaskClean_IsRunning()==0`(或全部危险输出已关)才执行;运行中收到的保存请求挂起,流程结束后补写。

## 5. 无看门狗,HardFault 后输出冻结在最后状态

- **位置**:`stm32f4xx_hal_conf.h:58`(IWDG 被注释);`stm32f4xx_it.c` 的 `HardFault_Handler` 是 `while(1)`;`main.c` `Error_Handler` 只闪灯
- **原因**:没有独立看门狗;fault 处理死循环,不复位、不关输出。
- **后果**:野指针/越界等引发 HardFault 时,加热棒、风机、泵保持最后状态,无人值守下可能持续加热。
- **复现**:调试器注入一次 HardFault(或构造空指针),观察输出全部保持。
- **解决**:启用 IWDG,各关键任务喂狗;`HardFault_Handler` 进死循环前先把危险输出写成安全电平(直接操作 GPIO 寄存器,不依赖 RTOS)。

## 6. 跨任务直接 Reset/memset 运行中的流程上下文(存疑,竞态窗口小)

- **位置**:`auto_process.c:192-211`(`AutoProcess_Reset`)、`:240-271`(`TerminateServiceToExit`),由 host232 任务直接调用(`app_iap.c` 多处);`clean_process.c:544-550` `CleanProcess_Reset` 被 `task_clean.c:202` 直接调用
- **原因**:auto 任务可能正停在 `AppFlow_Process` 的某个 action 里,host232 任务此时 `memset` 上下文、清阶段静态量、改 `current_stage`。被抢占的 action 拿着旧 step 指针继续跑,可能在"全关输出"之后又执行一次开水/开阀。
- **后果**:停止/终止服务命令后,危险输出存在被重新打开的竞态窗口(毫秒级,概率性,但方向是安全相关)。
- **复现**:难以稳定复现,走读可确认:流程运行中高频发"停止/终止服务",用日志或逻辑分析仪抓阀输出是否有停止后的瞬时 reopen。
- **解决**:停止/重置类命令只置请求标志,由 auto/clean 任务在自己下一轮 `Process` 里检测后自行关输出、清状态——属主任务单线程收尾,消除竞态。

## 7. 485 急停最坏延迟数秒,且清零后可能执行残留"开"命令

- **位置**:`task_comm485.c:814-851`(主循环)、`:398-407`(`RequestSafeStop` 重置队列)、`:212`(生产者阻塞式 `osMessageQueuePut`)、`:194-198`(inhibited 只在入队时检查)
- **原因**:三层叠加:① `safe_stop_requested` 只在主循环顶部查一次,单条命令对掉线站点最坏阻塞约 2 秒(发送0.5s+帧头0.5s+后续字节1s),清零自身又是 9~11 次串行交换;② 竞态:生产者因队列满阻塞在 Put → SafeStop 复位队列腾出空间 → Put 成功,一条"开"命令落在 reset **之后** → 清零执行完,这条残留命令又被排空执行;③ apply 执行时不复查 inhibited/急停。
- **后果**:急停后 485 加热/风机最坏数秒才断电;极端时序下清零后仍有执行器被打开。
- **复现**:拔掉一路 485 执行器(制造死站)并触发几条发往该站的命令,按急停,计时加热实际断电时间;竞态需高频手动 485 命令把队列打满再急停,概率性。
- **解决**:排空循环每执行一条命令后重查 `safe_stop_requested` 并跳出;`apply_*` 执行前重查 `nonzero_output_inhibited`/`AutoDevice_IsEmergencyStopped()`,非零命令直接丢弃;写命令响应超时从 500ms 压到约 100ms。

## 8. `keep_on_during_emergency` 是死配置,急停实际断排风/制氧

- **位置**:`task_output.c:24`(字段)、`:55-56`(排气扇/制氧机标 1)、`:280-284`(互锁函数从不读该字段,注释自承"不保留任何点位")
- **原因**:输出表逐点注释写着"急停时允许保持",实现却一刀切全断,两者矛盾。
- **后果**:急停瞬间舱内排风、制氧全停。舱内有宠物、舱温偏高、或气体积聚的场景下,是否符合产品安全预期,需要产品层面拍板——现在等于"配置表说了不算"。
- **复现**:自动模式下手动开排风,按急停 → 排风停转(与表注释矛盾)。
- **解决**:二选一:互锁里放行 `keep_on_during_emergency==1` 的点;或删掉字段、统一注释,避免后人误信配置表。

# 二、中等问题

## 9. 多处等待无超时,故障码定义了却不用

- **位置**:`auto_stage_wash_ready.c:72-114`(等水箱高液位、等水温达标)、`auto_stage_entry.c` / `auto_stage_exit.c`(等门开、等上位机命令)、门锁检测失败无限解锁重试
- **原因**:这些等待没有任何超时和上报,而 `AUTO_FAULT_TANK_HIGH_WAIT_TOO_LONG`、`AUTO_FAULT_TANK_TEMP_NOT_READY` 等故障码已定义。
- **后果**:水位传感器/温度传感器/门锁损坏时,流程**永久挂死**,上位机只看到"运行中",无任何故障提示。
- **复现**:拔掉水箱温度传感器,跑完整流程到洗前准备 → 永远停在等待水温。
- **解决**:参考 `clean_process.c:181-187` 的 300 秒超时上报模式,给这些等待统一加超时 FAIL + 上报;门锁重试加次数上限。

## 10. 自清洁左侧上层区域从未被清洗

- **位置**:`clean_process.c:264-266`(`SwitchLeftUpper`)
- **原因**:已知"步骤 70 直接跳 90"导致步骤 80 等待不执行;更严重的是该动作把 `SELF_CLEAN_FRONT_UPPER_VALVE` **写成 0**,全工程没有任何地方把它置 1。即使修好跳转,也是关着阀干等。
- **后果**:舱内左侧上层区域从交付起就没被自清洁洗到过。
- **复现**:触发自清洁,观察左上层清洁阀全程无动作。
- **解决**:跳转目标改回 80(让 `self_clean_left_upper_time_ms` 生效),`SwitchLeftUpper` 里把该阀置 1 并开计时。

## 11. 一路 485 掉线拖垮总线,连累传感器被误判过期

- **位置**:`thyristor.c:19`(单次响应超时 500ms,重试 2 次)、`task_comm485.c:17`(传感器 5 秒过期)
- **原因**:执行器命令和 4 路传感器轮询在同一任务里串行。一个掉线站点每次交换阻塞约 1.5~2 秒且全速重试,几条死站命令就能让某路传感器超过 5 秒没刷新。
- **后果**:本来正常的传感器数据被判 stale,流程以"传感器故障"FAIL——故障定位会被误导到传感器上。
- **复现**:拔掉一路 485 加热站,跑烘干,数分钟后观察温度/环境数据被判无效。
- **解决**:站点级失败计数退避——连续失败 N 次后跳过该站 M 个轮询周期,恢复后清零计数。

## 12. 恢复默认参数不落盘

- **位置**:`app_param.c:417-423` `AppParam_RestoreDefaults()`,调用点 `app_iap.c:1540`
- **原因**:只改 RAM 就回 ACK,不请求保存。
- **后果**:上位机以为已恢复出厂;中途断电重启后旧参数原样回来,上位机与设备认知不一致。
- **复现**:改一套配方 → 发恢复默认 → 断电重启 → 读参数,配方还是改的。
- **解决**:函数内补 `AppParam_RequestSave()`(配合问题 4 的门条件)。

## 13. 急停输入无消抖

- **位置**:`auto_device.c:447-450` 读原始引脚,`task_output.c:703/720` 每 10ms 直接使用
- **原因**:没有采样确认,单个毛刺即触发。
- **后果**:工业现场继电器群干扰下可能频繁误停机。方向是 fail-safe,所以只影响可用性。
- **复现**:急停回路附近继电器吸合时观察是否误触发停机。
- **解决**:加 2~3 次采样确认(20~30ms),仍远快于人的反应速度。

## 14. `auto_process` 跨任务共享标志缺 volatile

- **位置**:`auto_process.c:26-41`
- **原因**:`auto_running`、`auto_finished`、`auto_failed`、`clean_requested`、`full_request`、`current_stage`、`stage_start_tick` 都被 host232 和 auto 两个任务读写,却只有 `restart_current_stage_request` 和 `stage_test_request[]` 声明了 volatile(同文件标准不统一,`task_clean.c` 倒是全 volatile)。
- **后果**:字节访问在 Cortex-M 上不会撕裂,目前凑巧工作正常;但属 C 语义数据竞争,编译器优化等级变化后可能出诡异问题。
- **复现**:无法稳定复现,属隐患。
- **解决**:统一补 volatile。

## 15. 485 命令重试耗尽后静默丢弃,调用方拿到的是 HAL_OK

- **位置**:`task_comm485.c:213-217`(入队即返回 OK)、`:593-604`(重试耗尽只清标志)
- **原因**:请求是"入队即成功"的最终一致性设计,但丢弃时无任何日志/上报。
- **后果**:风机/加热/增压泵没设上,自动流程和自清洁都以为设上了,无人知晓。
- **复现**:拔一路执行器,跑烘干,抓 485 日志:设置命令丢了他无感知。
- **解决**:丢命令时至少打一条诊断日志(站号+命令类型),或定义故障上报。

## 16. 参数版本不匹配直接清空回默认

- **位置**:`app_param.c:170-183`
- **原因**:version 不等即 `load_defaults()+SaveNow()`,无迁移逻辑(当前已 0x0005)。
- **后果**:每次 `APP_PARAM_VERSION` 升级,现场 26 套配方全部丢回出厂。
- **复现**:改版本号编译烧录 → 原配方全丢。
- **解决**:相邻版本做保留式迁移(至少保住 recipes 区),或在升级流程文档明确告知会丢参数。
