# 自动流程运行说明

本文档用于配合代码理解自动流程框架。重点说明：

- 自动流程如何启动。
- 自动流程如何按阶段跳转。
- 每个小流程内部步骤如何运行。
- 单段小流程测试如何触发。
- 自动流程结束后如何触发自清洁。
- 水箱恒温和生命保障线程与自动流程是什么关系。

相关代码文件：

- `Core/Src/task_auto.c`
- `Core/Src/auto_process.c`
- `Core/Src/app_flow.c`
- `Core/Src/task_clean.c`
- `Core/Src/clean_process.c`
- `Core/Src/task_water_tank.c`
- `Core/Src/task_life_support.c`
- `Core/Src/task_output.c`

## 1. 总体结构

当前自动流程采用“线程 + 阶段表 + 步骤表”的方式。

整体可以理解成三层：

```text
task_auto.c
  自动流程线程，只负责周期调用 AutoProcess_Process()

auto_process.c
  自动流程总调度，负责大阶段跳转

app_flow.c
  通用流程执行器，负责执行某一个小流程里的每一步
```

也就是说：

```text
task_auto.c 调度 auto_process.c
auto_process.c 选择当前小流程
app_flow.c 执行当前小流程的步骤表
```

## 2. 自动流程有哪些阶段

自动流程阶段定义在 `Core/Inc/auto_process.h`：

```c
typedef enum
{
  AUTO_PROCESS_STAGE_ENTRY_ENV = 0,     /* 入舱准备 */
  AUTO_PROCESS_STAGE_ENTRY,             /* 入舱流程 */
  AUTO_PROCESS_STAGE_WASH_READY,        /* 洗前准备 */
  AUTO_PROCESS_STAGE_SPRAY,             /* 冲洗 */
  AUTO_PROCESS_STAGE_BATH,              /* 沐浴 */
  AUTO_PROCESS_STAGE_CLEAN,             /* 清洗 */
  AUTO_PROCESS_STAGE_DRY,               /* 吹干 */
  AUTO_PROCESS_STAGE_EXIT_PREPARE,      /* 出舱准备 */
  AUTO_PROCESS_STAGE_EXIT,              /* 出舱流程 */
  AUTO_PROCESS_STAGE_COUNT
} AutoProcessStage;
```

完整自动流程顺序是：

```text
入舱准备
  -> 入舱流程
  -> 洗前准备
  -> 冲洗
  -> 沐浴
  -> 清洗
  -> 吹干
  -> 出舱准备
  -> 出舱流程
  -> 自动流程完成
  -> 触发自清洁
```

这些阶段被整理成 `auto_process.c` 里的 `auto_stages[]`：

```c
static const AutoStage auto_stages[] = {
  {"入舱准备", stage_entry_env_steps, ...},
  {"入舱流程", stage_entry_steps, ...},
  {"洗前准备", stage_wash_ready_steps, ...},
  {"冲洗",     stage_spray_steps, ...},
  {"沐浴",     stage_bath_steps, ...},
  {"清洗",     stage_clean_steps, ...},
  {"吹干",     stage_dry_steps, ...},
  {"出舱准备", stage_exit_prepare_steps, ...},
  {"出舱流程", stage_exit_steps, ...},
};
```

每一行就是一个“小流程”。

## 3. 上电后自动流程会不会自己运行

不会。

`task_auto.c` 里只调用：

```c
AutoProcess_Init();
```

它只初始化状态，不启动自动流程。

也就是说，上电后自动流程线程会一直运行，但处于等待状态。真正启动需要调用下面接口之一：

```c
AutoProcess_RequestFull();
AutoProcess_RequestStageTest(...);
```

## 4. 完整自动流程如何启动

启动完整流程调用：

```c
AutoProcess_RequestFull();
```

这个函数不会立刻直接跑流程，而是只设置一个请求标志：

```c
full_request = 1U;
```

之后 `task_auto.c` 周期调用：

```c
AutoProcess_Process();
```

`AutoProcess_Process()` 发现当前没有流程运行时，会调用：

```c
start_pending_request();
```

然后 `start_pending_request()` 看到 `full_request != 0U`，就会：

```c
full_request = 0U;
AutoProcess_Start();
```

`AutoProcess_Start()` 做这些事：

```text
auto_running = 1
auto_finished = 0
auto_failed = 0
clean_requested = 0
stage_test_mode = 0
start_stage(0)
```

其中：

```c
start_stage(0U);
```

表示从第 0 个小流程开始，也就是“入舱准备”。

## 5. 单段小流程如何测试

手动调试时，可以只触发某一个小流程。

例如只测试冲洗：

```c
AutoProcess_RequestStageTest(AUTO_PROCESS_STAGE_SPRAY);
```

只测试吹干：

```c
AutoProcess_RequestStageTest(AUTO_PROCESS_STAGE_DRY);
```

这个函数只设置对应小流程的测试标志：

```c
stage_test_request[stage] = 1U;
```

之后 `AutoProcess_Process()` 会在空闲时扫描 `stage_test_request[]`。

如果发现某个小流程被置位，就会：

```text
清除这个测试请求标志
auto_running = 1
auto_finished = 0
auto_failed = 0
clean_requested = 0
stage_test_mode = 1
start_stage(对应阶段)
```

重点：

```c
stage_test_mode = 1U;
```

表示当前是“单段测试模式”。

单段测试模式下，该小流程跑完后会直接停止：

```text
不会继续跑后面的阶段
不会自动触发自清洁
```

这方便现场单独测试某一段动作。

## 6. 小流程是如何启动的

无论是完整流程还是单段测试，最终都会调用：

```c
start_stage(stage_index);
```

这个函数做三件事：

```c
current_stage = stage_index;

AppFlow_Init(&auto_flow,
             auto_stages[current_stage].name,
             auto_stages[current_stage].steps,
             auto_stages[current_stage].count);

AppFlow_Start(&auto_flow);
```

含义是：

```text
1. 记录当前正在运行哪个小流程。
2. 把这个小流程的名称、步骤表、步骤数量交给通用流程执行器。
3. 启动通用流程执行器，从该小流程的第一个步骤开始跑。
```

## 7. 每个小流程内部如何执行

每个小流程都有自己的步骤表，例如冲洗：

```c
static const AppFlowStep stage_spray_steps[] = {
  STEP(1,  "SPRAY_CHECK_ALLOW",    "确认门已关闭、生命保障正常、水温达标且无急停暂停"),
  STEP(2,  "SPRAY_CHECK_TEMP",     "再次确认冲洗水温在目标范围"),
  STEP(3,  "SPRAY_VALVE_ON",       "打开淋浴阀"),
  STEP(4,  "SPRAY_FLOW_LOW",       "设置初始出水流量为 20%"),
  ...
};
```

每个步骤都是一个 `AppFlowStep`：

```c
struct AppFlowStep
{
  uint16_t id;
  const char *name;
  const char *description;
  uint32_t delay_before_ms;
  uint32_t hold_ms;
  uint32_t delay_after_ms;
  AppFlowAction action;
};
```

每一步执行顺序固定为：

```text
动作前延时 delay_before_ms
  -> 执行动作 action
  -> 动作保持 hold_ms
  -> 动作后延时 delay_after_ms
  -> 下一步
```

当前用的 `STEP()` 宏默认把三个延时都设成 0：

```c
#define STEP(id, name, desc) \
  { (id), (name), (desc), 0U, 0U, 0U, AppFlow_ActionTodo }
```

所以现在所有步骤都会快速通过。

后续如果某一步需要延时，可以把这一行从：

```c
STEP(13, "AIR_FRESH_ON", "打开空气清新剂喷雾"),
```

改成完整写法：

```c
{13, "AIR_FRESH_ON", "打开空气清新剂喷雾", 0U, 5000U, 0U, Action_AirFreshOn},
```

含义是：

```text
动作前不等
执行 Action_AirFreshOn
保持 5000ms
动作后不等
```

## 8. app_flow.c 如何跳到下一步

`app_flow.c` 是通用流程执行器。

它内部用 `phase` 表示当前步骤执行到哪一段：

```text
APP_FLOW_PHASE_DELAY_BEFORE
APP_FLOW_PHASE_ACTION
APP_FLOW_PHASE_HOLD
APP_FLOW_PHASE_DELAY_AFTER
```

流程如下：

```text
DELAY_BEFORE
  delay_before_ms 到时间
  -> ACTION

ACTION
  action 返回 DONE
  -> HOLD

ACTION
  action 返回 RUNNING
  -> 留在 ACTION，下一周期继续调用 action

ACTION
  action 返回 FAIL
  -> 整个流程失败

HOLD
  hold_ms 到时间
  -> DELAY_AFTER

DELAY_AFTER
  delay_after_ms 到时间
  -> current_index++
  -> 回到 DELAY_BEFORE
```

如果 `current_index >= step_count`，说明这个小流程跑完：

```text
running = 0
finished = 1
```

## 9. 完整流程如何跳转到下一个小流程

`AutoProcess_Process()` 每周期都会调用：

```c
AppFlow_Process(&auto_flow);
```

然后判断当前小流程是否完成：

```c
if (AppFlow_IsFinished(&auto_flow) == 0U)
{
  return;
}
```

如果当前小流程完成，并且不是单段测试模式，就会：

```c
current_stage++;
```

然后判断还有没有后续小流程：

```c
if (current_stage < auto_stages数量)
{
  start_stage(current_stage);
}
else
{
  自动流程全部完成
}
```

所以完整流程的跳转逻辑是：

```text
当前小流程完成
  -> current_stage++
  -> 如果还有阶段，start_stage(current_stage)
  -> 如果没有阶段，自动流程完成
```

## 10. 自动流程结束后如何触发自清洁

完整自动流程所有阶段都完成后，会执行：

```c
auto_running = 0U;
auto_finished = 1U;
```

然后触发自清洁：

```c
if (clean_requested == 0U)
{
  clean_requested = 1U;
  TaskClean_Request();
}
```

`clean_requested` 的作用是防止重复触发自清洁。

`TaskClean_Request()` 会设置自清洁线程的事件标志：

```c
osEventFlagsSet(clean_event, CLEAN_EVENT_REQUEST);
```

自清洁线程 `task_clean.c` 平时阻塞等待这个事件：

```c
osEventFlagsWait(clean_event,
                 CLEAN_EVENT_REQUEST,
                 osFlagsWaitAny,
                 osWaitForever);
```

收到事件后开始执行：

```c
CleanProcess_Start();
```

然后循环：

```c
CleanProcess_Process();
```

## 11. 自清洁流程在哪里

自清洁线程在：

```text
Core/Src/task_clean.c
```

自清洁具体步骤表在：

```text
Core/Src/clean_process.c
```

这样拆的原因是：

```text
task_clean.c 只负责线程和事件
clean_process.c 只负责自清洁工艺步骤
```

后续要调整自清洁动作，主要改：

```c
self_clean_steps[]
```

不要把大量动作都塞进 `task_clean.c`。

## 12. 水箱恒温线程和自动流程的关系

水箱恒温线程在：

```text
Core/Src/task_water_tank.c
```

它是后台线程，不属于自动主流程。

它的职责是：

```text
待机时保持水箱中限位
待机时保持水箱温度范围
自清洁请求时补水到上限位
主流程用水阶段暂停，避免抢泵和阀
```

当前只是表驱动框架，真实条件判断后续还要接：

```text
当前自动流程阶段
水箱液位传感器
水箱水温传感器
阀门和水泵输出
```

## 13. 生命保障线程和自动流程的关系

生命保障线程在：

```text
Core/Src/task_life_support.c
```

它也是后台线程，但优先级比普通自动流程高。

它的职责不是普通调温调湿，而是安全保护：

```text
氧气严重不足
温度严重异常
湿度严重异常
噪音严重异常
关键传感器失效
```

后续真实逻辑接入后，它可以让自动流程进入故障保护。

## 14. 输出为什么不直接写 GPIO

自动流程、自清洁、水箱恒温、生命保障都不应该直接调用：

```c
HAL_GPIO_WritePin()
```

普通输出应该统一走：

```c
TaskOutput_Request(...)
```

原因是：

```text
手动/自动互锁要统一判断
急停和安全条件要统一判断
多个线程不能同时抢同一个输出点
以后查问题只需要看 task_output.c
```

## 15. 后续真实动作应该怎么接

现在所有步骤默认动作都是：

```c
AppFlow_ActionTodo
```

它会立即返回：

```c
APP_FLOW_STEP_DONE
```

所以现在流程只是框架，不会真的动作。

后续接真实动作时，比如冲洗打开淋浴阀，可以新增函数：

```c
static AppFlowStepResult Action_SprayValveOn(AppFlowContext *ctx,
                                             const AppFlowStep *step)
{
  (void)ctx;
  (void)step;

  TaskOutput_Request(APP_OUTPUT_SOURCE_AUTO,
                     APP_OUTPUT_POINT_0,
                     GPIO_PIN_SET);

  return APP_FLOW_STEP_DONE;
}
```

然后把步骤表从：

```c
STEP(3, "SPRAY_VALVE_ON", "打开淋浴阀"),
```

改成：

```c
{3, "SPRAY_VALVE_ON", "打开淋浴阀", 0U, 0U, 100U, Action_SprayValveOn},
```

这样这一动作就真正接入了输出线程。

## 16. 最常用调试入口

完整自动流程：

```c
AutoProcess_RequestFull();
```

单独测试冲洗：

```c
AutoProcess_RequestStageTest(AUTO_PROCESS_STAGE_SPRAY);
```

单独测试吹干：

```c
AutoProcess_RequestStageTest(AUTO_PROCESS_STAGE_DRY);
```

单独触发自清洁：

```c
TaskClean_Request();
```

## 17. 当前状态总结

当前代码已经具备：

```text
完整自动流程阶段表
单段小流程测试标志
通用步骤执行器
每步动作前/保持/动作后延时
自动结束后触发自清洁
水箱恒温后台线程框架
生命保障后台线程框架
输出仲裁线程框架
```

当前还没有接入真实硬件动作：

```text
步骤 action 目前大多还是 AppFlow_ActionTodo
传感器条件判断还没接
上位机启动/停止/单段测试命令还没接
故障码上报还没接
```

后续建议接入顺序：

```text
1. 先接手动/自动模式和上位机启动命令。
2. 再接 task_output.c 的实际 DO 点位。
3. 再逐段把自动流程步骤 action 替换成真实动作函数。
4. 最后补传感器判断、超时失败、故障上报。
```
