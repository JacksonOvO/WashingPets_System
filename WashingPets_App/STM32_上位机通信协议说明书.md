### 1.1 5 分钟理解整体通信

本项目包含两类通信：

1.  APP 业务通信：设备正常运行时使用，负责模式切换、自动流程控制、参数读写、状态上报、故障上报和传感器遥测。
2.  IAP 在线升级通信：设备升级 App 固件时使用，负责从 App 切换到 Bootloader、传输 `App.bin`、校验并启动新 App。

两类协议共用基础帧格式、SEQ、LEN、CRC16 和 ACK/NACK 命令号，但业务 CMD 和升级 CMD 的运行环境不同，禁止在错误运行环境下使用。

### 1.2 最小联调路径

业务联调建议先按以下顺序执行：

    打开串口
    -> QUERY_INFO，识别当前处于 APP 还是 Bootloader
    -> 若处于 APP，发送 QUERY_DEVICE_STATUS
    -> 读取参数 GET_PARAM_BLOCK
    -> 切换 AUTO：SET_WORK_MODE(AUTO)
    -> 接收 DEVICE_STATUS / INTERACTION_REQUEST / FAULT_EVENT / TELEMETRY
    -> 按 request_id 回复 PROCESS_INTERACTION

升级联调建议先按以下顺序执行：

    QUERY_INFO
    -> ENTER_UPGRADE
    -> 等待 RSP_BOOT_READY 或 QUERY_INFO 兜底确认 Bootloader 在线
    -> UPGRADE_START
    -> 按 offset 顺序发送 UPGRADE_DATA
    -> UPGRADE_END
    -> 等待 App 启动并发送 RSP_APP_READY
    -> APP_START_CONFIRM

## 2. 协议边界与系统总览

### 2.1 协议分层

| **协议类型** | **运行程序**           | **主要职责**                             | **典型 CMD**             |
|--------------|------------------------|------------------------------------------|--------------------------|
| APP 业务协议 | STM32 App              | 业务控制、状态上报、参数读写、故障遥测   | `0x30~0x43`、`0xA1~0xA7` |
| IAP 升级协议 | STM32 App + Bootloader | 进入升级、分包传输、Flash 写入、校验启动 | `0x10~0x25`、`0x90~0x93` |
| 公共响应     | App / Bootloader       | 命令成功或失败响应                       | `0xF0`、`0xF1`           |

### 2.2 物理串口说明

原始 APP 业务协议写明业务通信任务使用 `USART2`；原始 IAP 协议写明物理接口为 `USART1 经 RS232 电平转换芯片与上位机连接`。

**注意：**正式联调前必须由硬件设计确认最终上位机 RS232 接口对应的 MCU USART。若业务通信和 IAP 升级共用同一个物理 RS232 口，则 App 和 Bootloader 必须配置为同一个 USART、同一波特率和同一帧格式。若确实使用不同 USART，则上位机接线、切换逻辑和联调说明必须单独明确。

### 2.3 关键强制规则

1.  上位机必须按二进制帧发送，禁止开启串口文本转换、自动追加换行或本地回显。
2.  多字节整数必须采用小端序。
3.  新请求必须分配新的 SEQ；超时重发必须保持原 CMD、SEQ 和 Payload 不变。
4.  设备响应必须回显请求 SEQ。
5.  主动上报帧使用设备独立上报 SEQ；上位机不能只按 SEQ 去重，应按 `request_id` 或 `event_id` 去重。
6.  业务协议中的 `detail_u32` 与 IAP 升级协议中的 
ext_offset_u32` 字段位置相同，但语义不同。
7.  任何涉及门、急停、温度、液位、Flash 擦写的操作必须先进行安全互锁或状态检查。

# 第一部分：公共通信规范

### 2. 串口参数

App、Bootloader 和上位机必须使用完全相同的串口参数。

| **参数** | **默认值**        | **说明**                                                       |
|----------|-------------------|----------------------------------------------------------------|
| 波特率   | `115200 bit/s`    | 最终值可按现场线缆和抗干扰测试调整                             |
| 数据位   | `8`               | 8 位数据                                                       |
| 校验位   | `None`            | 无奇偶校验                                                     |
| 停止位   | `1`               | 1 位停止位                                                     |
| 流控     | `None`            | 不使用 RTS/CTS                                                 |
| 字节序   | Little Endian     | 所有多字节整数低字节先发送                                     |
| 收发方式 | 半双工式请求/应答 | RS232 电气链路可全双工，但升级协议同一时刻只保留一个待确认请求 |

推荐上位机关闭串口文本转换、行尾追加和本地回显，所有报文均按二进制发送。

### 3. V1.1 通用帧格式

#### 3.1 帧结构

    +-------+-------+-----+-----+-------+-------+---------+-------+-------+
    | HEAD1 | HEAD2 | CMD | SEQ | LEN_L | LEN_H | PAYLOAD | CRC_L | CRC_H |
    +-------+-------+-----+-----+-------+-------+---------+-------+-------+
    |  1B   |  1B   | 1B  | 1B  |  1B   |  1B   |  0..N   |  1B   |  1B   |
    +-------+-------+-----+-----+-------+-------+---------+-------+-------+

| **字段**  | **长度** | **说明**                                       |
|-----------|----------|------------------------------------------------|
| `HEAD1`   | 1        | 固定 `0x55`                                    |
| `HEAD2`   | 1        | 固定 `0xAA`                                    |
| `CMD`     | 1        | 命令字或响应字                                 |
| `SEQ`     | 1        | 请求序号，范围 `0x00~0xFF`，循环递增           |
| `LEN`     | 2        | Payload 字节数，小端；空 Payload 时为 `0x0000` |
| `PAYLOAD` | N        | 命令数据，最大长度见第三部分第 5 节（最大 Payload 256 B）                    |
| `CRC16`   | 2        | CRC16/CCITT-FALSE，小端发送                    |

总帧长：

    FRAME_SIZE = 2 + 1 + 1 + 2 + LEN + 2 = LEN + 8 字节

#### 3.2 帧 CRC16

CRC 计算范围从 `CMD` 开始，到 Payload 最后一个字节结束，不包含帧头和 CRC 字段本身。

    CRC_INPUT = CMD + SEQ + LEN_L + LEN_H + PAYLOAD

算法参数：

| **参数**       | **值**                     |
|----------------|----------------------------|
| 名称           | CRC-16/CCITT-FALSE         |
| Poly           | `0x1021`                   |
| Init           | `0xFFFF`                   |
| RefIn / RefOut | `false / false`            |
| XorOut         | `0x0000`                   |
| 发送顺序       | `CRC_L` 在前，`CRC_H` 在后 |

参考实现：

    uint16_t Protocol_Crc16CcittFalse(const uint8_t *data, uint16_t len)
    {
        uint16_t crc = 0xFFFFU;

        while (len-- > 0U)
        {
            crc ^= (uint16_t)(*data++) << 8;
            for (uint8_t i = 0U; i < 8U; ++i)
            {
                crc = ((crc & 0x8000U) != 0U)
                    ? (uint16_t)((crc << 1) ^ 0x1021U)
                    : (uint16_t)(crc << 1);
            }
        }
        return crc;
    }

#### 3.3 固件整体 CRC32

固件 CRC32 对 `App.bin` 从文件第 0 字节到最后一个有效字节计算，不包含串口帧字段，也不对最后一包补齐的 `0xFF` 计算。

| **参数**       | **值**                                  |
|----------------|-----------------------------------------|
| 名称           | CRC-32/ISO-HDLC（常见 IEEE CRC32）      |
| Poly           | `0x04C11DB7`，反射实现使用 `0xEDB88320` |
| Init           | `0xFFFFFFFF`                            |
| RefIn / RefOut | `true / true`                           |
| XorOut         | `0xFFFFFFFF`                            |

上位机在升级前计算一次；Bootloader 在收到 `UPGRADE_END` 后对 Flash 中 `fw_size` 字节重新计算并比较。

### 4. 序号、ACK/NACK 与重发

#### 4.1 SEQ 规则

1.  上位机为每个新请求分配一个 SEQ，收到成功响应后才递增。
2.  MCU 响应帧必须原样返回请求帧的 SEQ。
3.  请求超时后，上位机必须使用相同的 CMD、SEQ 和 Payload 重发，不能生成新 SEQ。
4.  MCU 应缓存最近一次已成功请求的 `CMD + SEQ + Payload CRC` 和响应帧。
5.  MCU 收到完全相同的重复请求时，只重发缓存响应，不得再次擦除或重复写 Flash。
6.  相同 SEQ 对应不同内容时，MCU 返回 `ERR_SEQ_CONFLICT`。
7.  SEQ 从 `0xFF` 自然回绕到 `0x00`。

固件数据包同时携带 `offset`。SEQ 用于识别通信层重复/乱序，offset 用于确定 Flash 位置和恢复发送进度，两者不能互相替代。

#### 4.2 通用响应

| **响应**   | **CMD** | **Payload**                                                               |
|------------|---------|---------------------------------------------------------------------------|
| `RSP_ACK`  | `0xF0`  | `request_cmd_u8, status_u8, next_offset_u32`                              |
| `RSP_NACK` | `0xF1`  | `request_cmd_u8, error_u8, expected_seq_u8, reserved_u8, next_offset_u32` |


ext_offset` 表示 Bootloader 下一包期望的固件偏移；非升级数据命令填 `0`。

#### 4.3 错误码

| **名称**              | **数值** | **含义**                                  | **上位机处理**                   |
|-----------------------|----------|-------------------------------------------|----------------------------------|
| `STATUS_OK`           | `0x00`   | 成功                                      | 进入下一步                       |
| `ERR_BAD_CMD`         | `0x01`   | 不支持的命令                              | 停止当前操作并检查双方协议版本   |
| `ERR_BAD_LENGTH`      | `0x02`   | Payload 长度错误                          | 检查组包程序，不盲目重试         |
| `ERR_BAD_CRC16`       | `0x03`   | 帧 CRC16 错误                             | 相同 SEQ 重发                    |
| `ERR_BAD_STATE`       | `0x04`   | 当前状态不允许执行                        | 查询状态后决定重试或退出         |
| `ERR_BUSY`            | `0x05`   | MCU 正在擦除/校验                         | 延时后相同 SEQ 重试              |
| `ERR_SEQ`             | `0x06`   | 序号不符合预期                            | 按返回的 expected_seq 和进度同步 |
| `ERR_SEQ_CONFLICT`    | `0x07`   | 相同序号但内容不同                        | 中止当前会话并重新开始           |
| `ERR_TARGET_MISMATCH` | `0x08`   | 目标产品/硬件不匹配                       | 禁止升级                         |
| 保留                  | `0x09`   | 保留，不使用                              | 不应发送                         |
| `ERR_SIZE`            | `0x0A`   | 固件为空或超出 App 区                     | 禁止升级                         |
| `ERR_OFFSET`          | `0x0B`   | offset、长度或对齐非法                    | 读取 next_offset 后修正          |
| `ERR_FLASH`           | `0x0C`   | Flash 擦写失败                            | 有限重试，失败则停止             |
| `ERR_FW_CRC32`        | `0x0D`   | 固件整体 CRC32 不一致                     | 重新开始完整升级                 |
| `ERR_APP_INVALID`     | `0x0E`   | App 向量表或有效标志非法                  | 保持 Bootloader 模式             |
| `ERR_TIMEOUT`         | `0x0F`   | MCU 会话接收超时                          | 查询进度或重新 BEGIN             |
| `ERR_CONFIG`          | `0x10`   | Bootloader Flash/UART配置尚未确认或不合法 | 停止升级并检查固件配置           |

CRC 错误时，如果 MCU 能可靠解析出 CMD 和 SEQ，可发送 NACK；如果帧头、长度或内容不足以安全解析，MCU直接丢弃，等待上位机超时重发。

## 4. APP 主动上报补充规则

APP 业务协议存在主动上报帧，包括 `DEVICE_STATUS`、`INTERACTION_REQUEST`、`FAULT_EVENT` 和 `TELEMETRY`。这些上报帧使用设备独立上报 SEQ，不参与上位机请求 SEQ 的递增。

| **上报 CMD**               | **是否建议上位机 ACK** | **去重依据**   | **建议周期 / 时机**                     |
|----------------------------|------------------------|----------------|-----------------------------------------|
| `0xA1 DEVICE_STATUS`       | 否                     | 状态内容       | 状态变化立即上报，每 5000 ms 补发心跳   |
| `0xA3 INTERACTION_REQUEST` | 是                     | `request_id`   | 未完成时每 1000 ms 重发                 |
| `0xA4 FAULT_EVENT`         | 严重故障建议 ACK       | `event_id`     | 故障发生、更新、解除时上报              |
| `0xA5 TELEMETRY`           | 是                     | SEQ + 时间和数据内容 | 建议 500~1000 ms 周期上报；上位机收到后立即 ACK |

## 5. ACK/NACK 字段语义对照

| **字段位置**   | **APP 业务协议含义**                                               | **IAP 升级协议含义**                                    |
|----------------|--------------------------------------------------------------------|---------------------------------------------------------|
| `Payload[0]`   | 被确认或拒绝的业务 CMD                                             | 被确认或拒绝的升级 CMD                                  |
| `Payload[1]`   | `status` 或业务错误码                                              | `status` 或升级错误码                                   |
| `Payload[2:5]` | `detail_u32`，例如模式、动作结果、`request_id`、`revision`、故障码 | 
ext_offset_u32`，表示 Bootloader 下一包期望的固件偏移 |

**注意：**上位机可以复用 `0xF0/0xF1` 的帧解析函数，但必须根据当前运行环境和被确认 CMD 判断第三个字段的语义。

# 第二部分：APP 业务协议

## 1. APP 业务流程总览

### 1.1 【多 CMD 组合流程】上位机推荐工作流程

#### 1.1.1 【CMD=0x10/0x30/0x40】建立连接实例

    打开串口
    -> QUERY_INFO 识别 APP/Bootloader
    -> 如果 run_mode=APP，发送 QUERY_DEVICE_STATUS
    -> 分别读取全局参数和 26 套配方
    -> 开始接收 A1 状态、A3 交互、A4 故障和 A5 遥测上报

#### 1.1.2 【CMD=0x31/0x32/0xA1/0xA3/0x33/0xA4/0xA5】启动自动流程实例

    SET_WORK_MODE(AUTO)
    -> 设备进入自动模式空闲层
    -> 上位机发送 PROCESS_CONTROL(action=1) 启动完整自动流程
    -> 接收设备主动上报的 DEVICE_STATUS
    -> 入舱完成后收到 INTERACTION_REQUEST(type=SELECT_RECIPE)
    -> 上位机选择配方并发送 PROCESS_INTERACTION(request_id, type, result=1, value=recipe_id)
    -> 设备从对应参数区读取配方，继续执行后续自动流程
    -> 其他等待步骤仍通过 INTERACTION_REQUEST/PROCESS_INTERACTION 交互
    -> 持续显示 DEVICE_STATUS 和 TELEMETRY
    -> 流程完成或故障

#### 1.1.3 【CMD=0x31/0x32/0xA1/0xA5】单阶段测试实例

    用户先切到手动模式：SET_WORK_MODE(MANUAL)
    -> 上位机发送 PROCESS_CONTROL(action=5, stage_id=目标阶段) 触发单阶段测试
    -> 设备 A1 上报 work_mode=3（单阶段测试模式），process_type=2
    -> 持续显示 DEVICE_STATUS 和 TELEMETRY
    -> 测试自然结束，或上位机发送 PROCESS_CONTROL(action=4) 主动停止
    -> 设备自动切回手动模式，A1 上报 work_mode=1

注意：单阶段测试只接受手动模式触发，设备不会代为切换模式；在自动等其他模式下触发会收到 NACK `BAD_STATE`。

#### 1.1.4 【CMD=0x40/0xA2/0x41/0x42】修改参数实例

    GET_PARAM_BLOCK
    -> 用户编辑
    -> 本地范围检查
    -> SET_PARAM_BLOCK(old revision)
    -> 设备校验并返回 new revision
    -> SAVE_PARAMS(new revision)
    -> 再次 GET_PARAM_BLOCK 核对

| **CMD** | **命令名称**             | **方向**     | **运行环境** | **使用场景**                                       | **请求 Payload**       | **响应 Payload**              | **成功处理**                               | **失败处理**                                | **超时和重发**                  | **示例报文** | **注意事项**                                   |
|---------|--------------------------|--------------|--------------|----------------------------------------------------|------------------------|-------------------------------|--------------------------------------------|---------------------------------------------|---------------------------------|--------------|------------------------------------------------|
| `0x30`  | `QUERY_DEVICE_STATUS`    | Host -\> MCU | APP          | 连接或重连时查询当前模式和流程状态                 | 空                     | `0xA1 DEVICE_STATUS`，12 字节 | 上位机刷新设备状态                         | 超时重发原帧                                | 2 秒，原 SEQ 重发               | 见 5.1       | 平时不建议持续轮询，主要依赖主动 A1            |

### 3. 【CMD=0x30/0x31/0x32/0xA1】设备模式和运行状态

#### 3.1 【CMD=0x31 设置，CMD=0xA1 上报】工作模式 `work_mode`

| **值** | **名称**     | **说明**                                                         |
|--------|--------------|------------------------------------------------------------------|
| 0      | `IDLE`       | 空闲/待机，不接受危险手动输出                                    |
| 1      | `MANUAL`     | 手动模式，上位机可发送允许的手动输出命令                         |
| 2      | `AUTO`       | 自动模式；切换成功后进入空闲层，等待完整流程或自清洁命令         |
| 3      | `SERVICE`    | 单阶段测试模式；仅由设备在手动模式下收到 `0x32 action=5` 后自动进入，上位机不能直接设置；测试结束自动回手动模式 |
| 4      | `FAULT`      | 故障锁定模式（当前版本故障时不上报该值，保留语义；故障以 `run_state=FAULTED` 体现） |
| 5      | `BOOTLOADER` | 仅用于上位机显示，APP 正常业务帧不会处于此值                     |

当前 `TaskOutput_SetAutoMode(1/0)` 只有自动/手动二值。单阶段测试期间设备内部临时使用自动输出仲裁（自动流程才能驱动输出），主机协议层 `work_mode` 上报 3（单阶段测试模式）；测试自然结束、主动停止或故障复位后设备自动切回手动模式。

活动故障（含 485 从站健康故障）时不额外把 `work_mode` 置为 4(FAULT)：自动模式下发生故障会由设备安全停机并切回手动，因此 A1 上报的 `work_mode` 为实际模式（通常为 1=MANUAL），故障体现在 `run_state=FAULTED`。值 4 保留给后续“故障锁定”语义，当前版本 APP 业务帧不会上报。

切换到 AUTO 的前置条件：急停触发、存在活动故障（`AutoDevice_GetFault()` 非 0）或任一 485 从站被健康巡检判定失联时，设备拒绝切自动，返回 NACK `BAD_STATE`，`detail` 携带首个故障码（可查 10.3 故障码表定位）。故障复位且失联从站恢复健康后才允许切换。

#### 3.2 【CMD=0x32 控制，CMD=0xA1 上报】运行状态 `run_state`

| **值** | **名称**    | **说明**           |
|--------|-------------|--------------------|
| 0      | `STOPPED`   | 未运行             |
| 1      | `STARTING`  | 正在启动流程       |
| 2      | `RUNNING`   | 正常执行           |
| 3      | `WAIT_HOST` | 等待上位机交互     |
| 4      | `PAUSED`    | 已暂停             |
| 5      | `STOPPING`  | 正在安全停机       |
| 6      | `FINISHED`  | 本次流程完成       |
| 7      | `FAULTED`   | 流程失败或安全故障 |

#### 3.3 【CMD=0x32 控制，CMD=0xA1 上报】过程类型 `process_type`

| **值** | **名称**     |
|--------|--------------|
| 0      | 无流程       |
| 1      | 完整自动流程 |
| 2      | 单阶段测试   |
| 3      | 自清洗流程   |
| 4      | 手动操作     |

### 4. 【CMD=0xF0/0xF1】通用 ACK/NACK

#### 4.1 【CMD=0xF0】ACK 成功响应

Payload 固定 6 字节：

| **偏移** | **长度** | **类型** | **说明**               |
|----------|----------|----------|------------------------|
| 0        | 1        | `uint8`  | 被确认的请求 CMD       |
| 1        | 1        | `uint8`  | 状态，成功为 0         |
| 2        | 4        | `uint32` | detail，按具体命令解释 |

业务命令中 `detail` 建议解释：

| **命令**              | **detail**                                                      |
|-----------------------|-----------------------------------------------------------------|
| `SET_WORK_MODE`       | 生效后的模式                                                    |
| `PROCESS_CONTROL`     | 生效后的动作结果；当前代码中 detail 通常回显 action 或 stage_id |
| `PROCESS_INTERACTION` | 已接受的 `request_id`                                           |
| `MANUAL_OUTPUT_CONTROL` | 已接受的 GPIO `output_id`                                     |
| `MANUAL_RS485_CONTROL`  | 已接受的 RS485 站号                                            |
| `SET_PARAM_BLOCK`     | 新参数 revision                                                 |
| `SAVE_PARAMS`         | 已保存的 revision                                               |

ACK 收发实例：主机设置自动模式，设备执行成功。

    主机发送 CMD=0x31，SEQ=1：
    55 AA 31 01 02 00 02 00 67 45
    55 AA 31 02 02 00 01 00 E6 FE
    设备回复 CMD=0xF0，SEQ=1：
    55 AA F0 01 06 00 31 00 02 00 00 00 20 36

中文说明：ACK Payload 中 `31 00` 表示 CMD `0x31` 成功，`02 00 00 00` 表示实际模式为自动模式 2。

#### 4.2 【CMD=0xF1】NACK 失败响应

Payload 固定 8 字节，兼容现有 IAP：

| **偏移** | **长度** | **类型** | **说明**                                      |
|----------|----------|----------|-----------------------------------------------|
| 0        | 1        | `uint8`  | 被拒绝的请求 CMD                              |
| 1        | 1        | `uint8`  | 错误码                                        |
| 2        | 1        | `uint8`  | 设备期望的 SEQ，业务协议可填当前请求 SEQ      |
| 3        | 1        | `uint8`  | 保留，填 0                                    |
| 4        | 4        | `uint32` | detail，例如参数 ID、request_id 或 fault_code |

业务命令的 NACK 复用上方 §4.3 的 IAP 错误码（0x01~0x10），固件不单独区分业务错误码。常见业务拒绝场景与错误码对照：

| **场景**                                                                  | **错误码**           |
|---------------------------------------------------------------------------|----------------------|
| 当前模式/运行状态不允许该操作（模式切换、流程控制、手动输出被自动模式或急停拒绝） | `0x04 ERR_BAD_STATE` |
| 设备忙 / 安全互锁拒绝 / 流程占用（手动输出互锁、流程无法启动、参数保存中忙）      | `0x05 ERR_BUSY`      |
| 参数 revision 冲突（参数已被其他请求修改，应重新读取）                        | `0x07 ERR_SEQ_CONFLICT` |
| Flash 擦写或回读失败（保存参数失败）                                        | `0x0C ERR_FLASH`     |
| 参数结构版本不匹配 / output_id 越界 / action 不支持 / 交互 request_id 已失效   | `0x10 ERR_CONFIG`    |
| Payload 长度错误                                                            | `0x02 ERR_BAD_LENGTH` |
| 帧 CRC 错误                                                                | `0x03 ERR_BAD_CRC16` |

`0x11~0x1A` 业务错误码（INVALID_MODE/INVALID_STATE/INTERLOCK_REJECTED 等）当前版本**预留、固件不发送**；将来如需精确拒绝语义可在此启用，并同步更新上位机 `server.py` 的错误码映射。

NACK 回复实例：设备拒绝模式切换。

    设备回复 CMD=0xF1，SEQ=9：
    55 AA F1 09 08 00 31 04 09 00 02 00 00 00 52 FC

中文说明：被拒绝的是 CMD `0x31`，错误码 `0x04=ERR_BAD_STATE`（当前状态不允许），detail 为 2。

### 5. 【CMD=0x30/0xA1】查询和主动上报设备状态

#### 5.1 【CMD=0x30】`QUERY_DEVICE_STATUS` 主机查询状态

主机 Payload：空。 设备响应：立即发送 `DEVICE_STATUS 0xA1`，SEQ 回显请求 SEQ。 发送实例：

    主机发送 CMD=0x30，SEQ=0，Payload 为空：
    55 AA 30 00 00 00 29 A8

中文说明：设备收到后必须回复同一个 SEQ 的 CMD `0xA1`。平时不需要上位机持续轮询，A1 由设备主动发送。若当前存在故障，设备紧接着主动发送一帧 A4，便于上位机重连后恢复故障显示。

#### 5.2 【CMD=0xA1】`DEVICE_STATUS` 状态响应/主动上报

设备应在以下情况发送： 1. 收到状态查询时立即响应。 2. 工作模式、运行状态、阶段或步骤发生变化时立即主动上报。 3. 状态无变化时每 5000 ms 补发一次心跳。Payload 固定 12 字节，只传递运行任务需要的核心状态：

| **偏移** | **长度** | **类型** | **说明**                                                      |
|----------|----------|----------|---------------------------------------------------------------|
| 0        | 1        | `uint8`  | `work_mode`：设备工作模式，空闲/手动/自动/单阶段测试；故障时上报实际模式（自动模式安全停机后为手动），故障由 `run_state=FAULTED` 体现 |
| 1        | 1        | `uint8`  | `run_state`：当前流程状态，停止/启动/运行/等待/暂停/完成/故障 |
| 2        | 1        | `uint8`  | `process_type`：当前过程类型，完整自动/单阶段测试/自清洗/手动 |
| 3        | 1        | `uint8`  | `stage_id`：当前自动流程阶段编号，例如 3 表示冲洗             |
| 4        | 2        | `uint16` | `step_id`：当前阶段内部的步骤编号                             |
| 6        | 1        | `uint8`  | `step_state`：步骤状态，进入/运行/等待/完成/失败              |
| 7        | 1        | `uint8`  | `recipe_id`：当前流程使用的配方编号，0~25；无配方时填 `0xFF`   |
| 8        | 2        | `uint16` | `progress_x10`：总进度，0~1000，450 表示 45.0%                |
| 10       | 1        | `uint8`  | `result`：流程或步骤结果，0=无错误，其他值为结束原因或错误码  |
| 11       | 1        | `uint8`  | `reserved`：保留字段，当前固定填 0                            |

回复实例：

    设备回复或主动发送 CMD=0xA1，SEQ=0，LEN=12：
    55 AA A1 00 0C 00 02 02 01 03 08 00 01 00 C2 01 00 00 5B 4C

中文说明：设备处于自动模式，正在运行完整自动流程，使用配方 0，当前处于冲洗阶段步骤 8，步骤正在运行，总进度 45.0%，当前结果为正常。

### 6. 【CMD=0x31/0x32】模式和流程控制

#### 6.1 【CMD=0x31】`SET_WORK_MODE` 设置工作模式

Payload：

| **偏移** | **长度** | **类型** | **字段名及中文说明**                                                                         |
|----------|----------|----------|----------------------------------------------------------------------------------------------|
| 0        | 1        | `uint8`  | `target_work_mode`：要求设备切换到的目标工作模式；0=空闲，1=手动，2=自动，3=单阶段测试（仅设备内部进入，上位机不应直接设置） |
| 1        | 1        | `uint8`  | `reserved`：保留字段，当前固定填 0                                                           |

规则： 1. 自动流程运行中禁止直接切手动，应先安全停止。 2. 急停或严重故障存在时禁止进入 AUTO。 3. 进入 MANUAL 时危险输出先回安全状态。 4. 设备上电后的默认模式为 MANUAL 手动模式，不会自行启动自动流程。 5. 从 MANUAL 成功切换到 AUTO 时只进入自动模式空闲层，不启动任何流程。 6. 空闲层可接受 `CMD=0x32 action=1` 完整流程或 `action=6` 自清洁请求。 7. 单阶段测试（`0x32 action=5`）仅在手动模式（MANUAL）下接受；其他模式触发返回 NACK `BAD_STATE`，设备不会代为切换模式，上位机必须先发送 `CMD=0x31` 切到手动模式。 8. 单阶段测试运行期间 `work_mode` 上报 3（单阶段测试模式）；测试自然结束、主动停止（`action=4`）或故障复位（`action=7`）后，设备自动回到手动模式。 9. 成功返回 ACK，detail 为实际生效模式。 收发实例：

    主机发送 CMD=0x31，设置 work_mode=2 自动模式：
    55 AA 31 01 02 00 02 00 67 45
    设备回复 ACK：
    55 AA F0 01 06 00 31 00 02 00 00 00 20 36

中文说明：设备完成模式切换，ACK detail=2。此时设备处于自动模式空闲层，尚未启动任何流程。

#### 6.2 【CMD=0x32】`PROCESS_CONTROL` 启停/暂停/继续流程

Payload 固定 4 字节，用于自动流程开始后的暂停、继续、停止、终止服务、单阶段测试、自清洗和清除故障锁存：

| **偏移** | **长度** | **类型** | **说明**                                                              |
|----------|----------|----------|-----------------------------------------------------------------------|
| 0        | 2        | `uint16` | `action`：流程控制动作，完整启动/暂停/继续/结束/终止服务/单阶段测试/自清洗/清除故障 |
| 2        | 2        | `uint16` | `stage_id`：目标阶段编号，仅单阶段测试使用                                |

action：

| **值** | **名称**     | **对应 APP 接口**                                                                                         |
|--------|--------------|-----------------------------------------------------------------------------------------------------------|
| 1      | 启动完整流程 | 仅自动模式空闲时调用 `AutoProcess_RequestFull()`                                                          |
| 2      | 暂停         | `AutoDevice_SetPaused(1)`                                                                                 |
| 3      | 继续         | `AutoDevice_SetPaused(0)`                                                                                 |
| 4      | 安全停止     | `AutoDevice_SetStopRequested(1)`                                                                          |
| 5      | 单阶段测试   | 仅手动模式接受；接受后调用 `AutoProcess_RequestStageTest(stage_id)`，运行期间 `work_mode` 上报 3，结束/停止/故障复位后自动回手动模式 |
| 6      | 启动自清洗   | `TaskClean_Request()`                                                                                     |
| 7      | 清除故障锁存 | `AutoDevice_ClearFault()` + `AutoDevice_SetPaused(0)` + `AutoDevice_SetStopRequested(0)` + `AutoProcess_Reset()` |
| 8      | 终止服务     | 关闭当前动作输出；若仍在入舱环境调整阶段则直接结束且不自清洁，若已进入入舱流程或后续阶段则跳到出舱流程，出舱完成后继续自清洁 |

中文说明： 1. `action=7` 现在已经实现，可由上位机直接调用。 2. 这个动作是“清除故障锁存/复位流程状态”，不是“整机软件重启”。 3. 执行成功后，设备会清掉当前故障锁存、清掉暂停和停止请求，并复位自动流程状态机。 4. 如果急停输入仍然有效，或者真实硬件故障条件仍未解除，设备可能在后续扫描中再次进入故障状态。 5. 发送 `action=7` 成功后，建议上位机立即等待一帧新的 `A1 DEVICE_STATUS`，必要时再结合 `A4 FAULT_EVENT` 刷新故障显示。 6. `action=8` 为终止服务按钮使用：仅自动流程运行中有效。设备会先关闭当前动作输出；如果当前仍在入舱环境调整阶段，流程直接结束，不进入出舱流程，也不启动自清洁；如果已经进入入舱流程或后续阶段，设备会直接进入出舱流程，出舱完成后按完整自动流程收尾逻辑继续自清洁。 7. `action=5` 单阶段测试仅在手动模式接受：上位机必须先用 `CMD=0x31` 切到手动模式再发送 `CMD=0x32 action=5`，设备不会代为切换模式；单阶段测试运行期间 A1 的 `work_mode` 上报 3（单阶段测试模式）；自然结束、主动停止（`action=4`）或故障复位（`action=7`）后自动回到手动模式。 收发实例：暂停当前自动流程。

    主机发送 CMD=0x32，action=2，stage_id=0：
    55 AA 32 02 04 00 02 00 00 00 6E 73
    设备回复 ACK，detail=4 表示已经进入 PAUSED：
    55 AA F0 02 06 00 32 00 04 00 00 00 1D F2

中文说明：切换到自动模式后，使用 `CMD=0x32 action=1` 启动完整自动流程。 收发实例：清除故障锁存。

    主机发送 CMD=0x32，SEQ=3，action=7，stage_id=0：
    55 AA 32 03 04 00 07 00 00 00 4A 77
    设备回复 ACK，detail=7 表示已执行 action=7：
    55 AA F0 03 06 00 32 00 07 00 00 00 E2 82

中文说明：这条命令不会让 MCU 重启，只会清除当前故障锁存和自动流程故障状态。若需要重新启动自动流程，应在故障条件解除且处于自动模式后，发送 `CMD=0x32 action=1`。

### 7. 【CMD=0xA1】自动流程阶段和主动上报时机

#### 7.1 【CMD=0xA1 字段定义】阶段编号

| **stage_id** | **名称**                 | **当前步骤数** |
|--------------|--------------------------|----------------|
| 0            | 入舱环境准备 `ENTRY_ENV` | 14             |
| 1            | 入舱 `ENTRY`             | 20             |
| 2            | 洗前准备 `WASH_READY`    | 18             |
| 3            | 冲洗 `SPRAY`             | 16             |
| 4            | 沐浴 `BATH`              | 12             |
| 5            | 清洗 `CLEAN`             | 12             |
| 6            | 吹干 `DRY`               | 11             |
| 7            | 出舱准备 `EXIT_PREPARE`  | 4              |
| 8            | 出舱 `EXIT`              | 12             |
| 9            | 自清洗 `SELF_CLEAN`      | 25             |

`step_id` 使用各 `auto_stage_*.c` 中 `AUTO_STEP()` 的数字 ID。上位机显示文字建议按 `stage_id + step_id` 建立本地字典，不在每帧中传中文字符串。

#### 7.2 【CMD=0xA1】`DEVICE_STATUS` 主动上报时机

发送时机： 1. 工作模式发生变化。 2. 流程开始、暂停、继续、结束或失败。 3. `stage_id` 或 `step_id` 发生变化。 4. 进入或退出等待上位机状态。 Payload 统一使用 5.2 节定义的 12 字节 `DEVICE_STATUS`，不再额外定义流程状态帧。 step_state：

| **值** | **说明**        |
|--------|-----------------|
| 0      | 进入步骤        |
| 1      | 步骤运行中      |
| 2      | 等待传感器/条件 |
| 3      | 等待上位机      |
| 4      | 步骤完成        |
| 5      | 步骤失败        |
| 6      | 流程完成        |

建议在 `AppFlow_Process()` 首次进入 ACTION 时调用统一上报钩子，而不是发送调试 ASCII 文本。主动发送实例与 5.2 节相同，仅 SEQ 使用设备主动发送序号。

### 8. 【CMD=0xA3/0x33】自动流程中的上位机交互

#### 8.1 【CMD=0xA3 请求，CMD=0x33 回复】交互类型

| **interaction_type** | **名称**         | **当前 AutoCommand**                     |
|----------------------|------------------|------------------------------------------|
| 1                    | 打开上舱门       | `AUTO_COMMAND_OPEN_UPPER_DOOR`           |
| 2                    | 打开下舱门       | `AUTO_COMMAND_OPEN_LOWER_DOOR`           |
| 3                    | 关闭下舱门       | `AUTO_COMMAND_CLOSE_LOWER_DOOR`          |
| 4                    | 关闭上舱门       | `AUTO_COMMAND_CLOSE_UPPER_DOOR`          |
| 5                    | 继续流程         | `AUTO_COMMAND_CONTINUE`                  |
| 6                    | 选择本次运行配方 | 洗前准备阶段设备请求上位机返回 `recipe_id + bath_liquid_selection` |
| 7                    | 自动关门信号     | `AUTO_COMMAND_AUTO_CLOSE_DOOR`           |

#### 8.2 【CMD=0xA3】`INTERACTION_REQUEST` 设备请求上位机操作

当流程进入等待上位机步骤时，设备主动发送固定 8 字节 Payload：

| **偏移** | **长度** | **类型** | **说明**                                                   |
|----------|----------|----------|------------------------------------------------------------|
| 0        | 4        | `uint32` | `request_id`：本次上位机交互请求编号，每次请求递增         |
| 4        | 1        | `uint8`  | `interaction_type`：要求上位机执行的操作，例如开上门或继续 |
| 5        | 1        | `uint8`  | `stage_id`：发起请求时所在的流程阶段                       |
| 6        | 2        | `uint16` | `step_id`：发起请求时所在的步骤                            |

设备应每 1000 ms 重发未完成的交互请求，直到收到匹配回复，或因停止、故障、模式切换而取消当前流程。 主动请求实例：

    设备发送 CMD=0xA3，request_id=1，请求打开上舱门：
    55 AA A3 0B 08 00 01 00 00 00 01 01 01 00 3E E0

中文说明：设备正处于入舱阶段 1、步骤 1，等待上位机确认打开上舱门。

#### 8.3 【CMD=0x33】`PROCESS_INTERACTION` 主机回复交互请求

主机回复：

| **偏移** | **长度** | **类型** | **说明**                                                             |
|----------|----------|----------|----------------------------------------------------------------------|
| 0        | 4        | `uint32` | `request_id`：被回复的请求编号，必须与设备当前请求一致               |
| 4        | 1        | `uint8`  | `interaction_type`：被确认的交互类型；通常必须与设备请求一致，关门请求允许用 7 表示自动关门 |
| 5        | 1        | `uint8`  | `result`：上位机处理结果，1=确认执行，0=拒绝或取消                   |
| 6        | 2        | `uint16` | `value`：交互附加值；选择配方时低 8 位填写 `recipe_id`（0~25），高 8 位填写 `bath_liquid_selection`（0~3），其他交互填 0 |

设备校验 `request_id + interaction_type`；`stage_id/step_id` 仅用于上位机显示和日志定位，当前 APP 不再用它们拦截交互回复。门、自动关门和继续类交互调用对应 `AutoDevice_SetCommand()`；选择配方交互校验 `value` 后设置本次运行配方和本次沐浴液选择，并继续流程。

选择配方交互的 `value` 位域：

| **位段** | **字段** | **范围** | **说明** |
|----------|----------|----------|----------|
| bit0~7   | `recipe_id` | `0~25` | 本次运行使用的工艺配方编号 |
| bit8~15  | `bath_liquid_selection` | `0~3` | 本次沐浴/喷泡沫阶段使用的液路选择 |

`bath_liquid_selection` 定义：

| **值** | **液路** | **输出点** |
|--------|----------|------------|
| 0      | 沐浴液阀 | OUT13-PB6 |
| 1      | 芬香液阀 | OUT14-PB7 |
| 2      | 柔顺液阀 | OUT15-PB8 |
| 3      | 除螨液阀 | OUT16-PB9 |

关门交互的特殊规则：出舱流程先请求 `interaction_type=3` 关闭下舱门，之后请求 `interaction_type=4` 关闭上舱门；在等待关闭下舱门或关闭上舱门期间，上位机可以用同一个 `request_id` 回复 `interaction_type=7` 自动关门信号，APP 会接受该回复并触发 `AUTO_OUTPUT_DOOR_CLOSE` 闭门器输出。若用户手动关门，APP 检测到对应舱门到位后会直接触发相应电磁锁；若收到自动关门信号，APP 会等待需要关闭的舱门到位，再关闭闭门器输出并锁门。重要：不能只设置一个永久命令标志。使用 `request_id` 可以防止延迟到达的旧“开门”命令被下一轮流程误用。 正式联调时必须设置：

    #define AUTO_DEVICE_HOST_COMMAND_BYPASS 0U

收发实例：

    主机发送 CMD=0x33，确认 request_id=1、interaction_type=1：
    55 AA 33 03 08 00 01 00 00 00 01 01 00 00 70 EC
    设备回复 ACK，detail=request_id=1：
    55 AA F0 03 06 00 33 00 01 00 00 00 DB E0

中文说明：设备校验 request_id 后调用 `AutoDevice_SetCommand(AUTO_COMMAND_OPEN_UPPER_DOOR)`，流程进入上门解锁步骤。 选择配方收发实例：洗前准备阶段选择配方 2，并选择芬香液阀。

    设备主动请求配方，CMD=0xA3，SEQ=12，request_id=2，interaction_type=6：
    55 AA A3 0C 08 00 02 00 00 00 06 02 01 00 8B 09
    主机回复 CMD=0x33，SEQ=4，result=1，value=0x0102（低8位配方2，高8位洗剂选择1）：
    55 AA 33 04 08 00 02 00 00 00 06 01 02 01 D6 2A
    设备接受配方后回复 ACK，detail=request_id=2：
    55 AA F0 04 06 00 33 00 02 00 00 00 AC CA

中文说明：设备在洗前准备阶段暂停后续工艺并请求配方。上位机选择配方 2、沐浴液选择 1，设备读取参数区中配方 2 的数据，并在沐浴/喷泡沫阶段打开 OUT14-PB7 芬香液阀，然后继续执行后续流程。配方选择和沐浴液选择只对本次运行生效，不写入 Flash；只有修改配方参数时才执行 CMD=0x41/0x42 保存。

### 9. 【CMD=0x40/0x41/0x42/0x43/0xA2】参数协议

#### 9.1 【参数类 CMD 公共规则】设计原则

1.  不直接发送 `AppParam_t` 的裸内存，避免编译器 padding、字节对齐和结构升级问题。
2.  使用固定参数块和明确偏移。
3.  参数修改先进入 RAM，校验通过后 ACK。
4.  主机显式发送 `SAVE_PARAMS` 后写入 Sector 10。
5.  使用 revision 防止多个界面或请求相互覆盖。

#### 9.2 【CMD=0x40/0x41/0xA2 字段定义】参数组

| **group** | **内容** | **index** |
|-----------|----------|-----------|
| 0         | 全局参数 | 固定 0    |
| 1         | 工艺配方 | `0~25`    |

配方 ID：

| **index** | **配方** |
|-----------|----------|
| 0         | 短毛小型 |
| 1         | 短毛大型 |
| 2         | 长毛小型 |
| 3         | 长毛大型 |

#### 9.3 【CMD=0x40】`GET_PARAM_BLOCK` 读取参数

Payload：

| **偏移** | **长度** | **类型** | **字段名及中文说明**                                                      |
|----------|----------|----------|---------------------------------------------------------------------------|
| 0        | 1        | `uint8`  | `group`：要读取的参数组；0=全局参数，1=工艺配方参数                       |
| 1        | 1        | `uint8`  | `index`：参数组内的索引；读取全局参数时固定填 0，读取配方时填配方编号 0~25 |

设备响应 `PARAM_BLOCK 0xA2`。 发送实例：读取全局参数 group=0、index=0。

    主机发送 CMD=0x40，SEQ=5：
    55 AA 40 05 02 00 00 00 3F AA

中文说明：Payload `00 00` 分别表示全局参数组和索引 0。

#### 9.4 【CMD=0xA2】`PARAM_BLOCK` 参数读取响应

Payload 头：

| **偏移** | **长度** | **类型**  | **说明**                                                                         |
|----------|----------|-----------|----------------------------------------------------------------------------------|
| 0        | 1        | `uint8`   | `group`：参数组编号，0=全局参数，1=工艺配方                                      |
| 1        | 1        | `uint8`   | `index`：参数组内索引；全局参数固定 0，配方为 0~25                                |
| 2        | 2        | `uint16`  | `protocol_version`：参数数据结构版本，当前为 1；上位机应检查版本后再解析参数数据 |
| 4        | 4        | `uint32`  | `revision`：当前参数修订号，用于防止旧页面覆盖新参数                             |
| 8        | 2        | `uint16`  | `data_length`：后续参数数据区的字节数                                            |
| 10       | N        | `uint8[]` | `data`：参数数据区；具体字段布局由 `group` 决定，见后面的全局参数表和配方参数表  |

回复实例：

    设备回复 CMD=0xA2，SEQ=5，revision=2，data_length=16：
    55 AA A2 05 1A 00 00 00 01 00 02 00 00 00 10 00 32 01
    05 00 E8 03 00 00 60 EA 00 00 00 00 00 00 0D DC

中文说明：默认百分比 50%，Modbus 站号 1，PWM 频率 5，自动周期 1000ms，自清洗周期 60000ms；末尾 4 字节为保留字段。

#### 9.5 【CMD=0xA2/0x41，group=0】全局参数块字段

| **数据偏移** | **长度** | **类型**   | **当前字段**                                                       |
|--------------|----------|------------|--------------------------------------------------------------------|
| 0            | 1        | `uint8`    | `default_percent`：设备上电后的默认可控硅输出百分比，范围 0~100%   |
| 1            | 1        | `uint8`    | `thyristor_station`：可控硅控制器的 Modbus 站号，范围 1~247        |
| 2            | 2        | `uint16`   | `pwm_frequency`：预留的 PWM 频率参数；当前代码尚未实际使用         |
| 4            | 4        | `uint32`   | `auto_period_ms`：自动流程调度周期配置，单位 ms；当前属于预留参数  |
| 8            | 4        | `uint32`   | `clean_period_ms`：计划执行自清洗的周期，单位 ms；当前默认 60000ms |
| 12           | 4        | `uint8[4]` | `reserved`：保留字段，当前固定填 0；本次运行配方不属于掉电保存参数 |

#### 9.6 【CMD=0xA2/0x41，group=1】配方参数块字段

#### 9.7 【CMD=0x41】`SET_PARAM_BLOCK` 修改参数

Payload 与 `PARAM_BLOCK` 一致。`revision` 填主机读取到的旧 revision。 设备处理： 1. 检查参数协议版本、group、index、data_length。 2. 检查 revision 是否仍一致。 3. 校验每个值的上下限和组合关系。 4. 自动流程运行期间原则上禁止修改当前活动配方；也可接受修改但规定下次流程生效。 5. 更新 RAM 参数。 6. revision 加 1。 7. 返回 ACK，detail 为新 revision。 收发实例：主机基于 revision=2 修改全局参数。

    主机发送 CMD=0x41，SEQ=6：
    55 AA 41 06 1A 00 00 00 01 00 02 00 00 00 10 00 32 01
    05 00 E8 03 00 00 60 EA 00 00 00 00 00 00 60 5D
    设备回复 ACK，新 revision=3：
    55 AA F0 06 06 00 41 00 03 00 00 00 A3 B4

中文说明：参数已更新到 RAM，但还需要 CMD `0x42` 才能确认立即写入 Flash。

#### 9.8 【CMD=0x42】`SAVE_PARAMS` 保存参数到 Flash

Payload：

| **偏移** | **长度** | **类型** | **说明**                                                                                             |
|----------|----------|----------|------------------------------------------------------------------------------------------------------|
| 0        | 4        | `uint32` | `revision`：要求写入 Flash 的参数修订号，必须等于最近一次 CMD=0x41 修改成功后设备 ACK 返回的新修订号 |

设备调用 `AppParam_SaveNow()`。Flash 写入和回读成功后返回 ACK；失败返回 `SAVE_FAILED`。 收发实例：保存 revision=3。

    主机发送 CMD=0x42，SEQ=7：
    55 AA 42 07 04 00 03 00 00 00 71 CC
    设备擦写 Sector 10 成功后回复 ACK：
    55 AA F0 07 06 00 42 00 03 00 00 00 60 91

中文说明：只有收到此 ACK，上位机才显示“参数已保存”；如果返回 `SAVE_FAILED`，参数可能只在 RAM 中有效。 建议上位机操作顺序：

    GET_PARAM_BLOCK
    显示并编辑
    SET_PARAM_BLOCK
    收到新 revision
    SAVE_PARAMS(new revision)
    重新 GET_PARAM_BLOCK 校验显示

#### 9.9 【CMD=0x43】`RESTORE_DEFAULT_PARAMS` 恢复默认参数

为避免误操作，Payload 固定为 ASCII `DFLT`，十六进制为 `44 46 4C 54`。

    主机发送 CMD=0x43，SEQ=8：
    55 AA 43 08 04 00 44 46 4C 54 27 C3
    设备恢复默认值后回复 ACK，新 revision=4：
    55 AA F0 08 06 00 43 00 04 00 00 00 B9 1D

中文说明：设备恢复 RAM 默认值并生成新 revision。建议上位机随后发送 CMD `0x42` 保存到 Flash。

以下范围应由产品最终确认，协议实现至少需要校验：

| **字段**     | **建议范围**      |
|--------------|-------------------|

| 温度容差     | `0.1~20.0 摄氏度` |

### 10. 【CMD=0xA4】故障协议

#### 10.1 【CMD=0xA4】`FAULT_EVENT` 故障主动上报

Payload 固定 8 字节，只传递故障处理需要的数据；A4 不再携带 `fault_bitmap`，上位机只依据 `primary_fault_code` 显示具体报警。

| **偏移** | **长度** | **类型** | **说明**                                                            |
|----------|----------|----------|---------------------------------------------------------------------|
| 0        | 4        | `uint32` | `event_id`：故障事件编号，每次新故障事件递增，用于上位机去重        |
| 4        | 1        | `uint8`  | `event_type`：事件类型，1=故障发生，2=故障信息更新，3=故障解除      |
| 5        | 1        | `uint8`  | `severity`：故障等级，1=提示，2=警告，3=停机，4=急停                |
| 6        | 2        | `uint16` | `primary_fault_code`：本次事件的主要故障码；0 表示无故障            |

补充：APP 固件内部仍保留健康巡检状态，用于判断传感器与 485 从站故障发生、恢复和聚合上报时机；但这些内部状态不再通过 A4 位图外发。`primary_fault_code` 取值优先级为：① `AutoDevice_GetFault()` 中保存的 `AutoFaultCode`；② 若其为 0，则取健康巡检对应的具体从站/传感器故障码（`TaskComm485_GetFirstHealthFault()`，如比例阀断连时为 `0x0809`）；③ 两者皆无时，传感器类故障兼容填 `1`，超时类故障兼容填 `2`（旧路径兜底）。

`event_type` 已全部启用：`1=故障发生`（新故障码上报）；`2=故障信息更新`（当前活动故障码变化）；`3=故障解除`（无主故障码；`action=7` 故障复位后也会主动补发）。上位机收到 `event_type=3` 或 `primary_fault_code=0` 应清除故障显示。

| 33       | 4        | `uint32` | `total_remaining_time_ms`：从当前流程位置到烘干结束的总剩余时间，单位 ms，小端 |
| 37       | 4        | `uint32` | `current_stage_remaining_time_ms`：当前小流程剩余时间，单位 ms，小端；仅冲洗、沐浴、清洗、烘干阶段有值，其它阶段返回 0 |

功率和角度字段表示 APP 最近一次 485 写入成功后的确认目标值，用于上位机趋势显示和流程调试；增压泵压力字段例外，来自 1 号增压泵寄存器 `0x1010` 的实时压力反馈。设置增压泵压力后，APP 会读取设定值寄存器 `0x100F` 校验是否设置成功。急停、安全停机或流程结束触发全部关闭时，APP 会在关闭命令写入成功后把对应确认值更新为 0。

时间字段说明：`total_remaining_time_ms` 表示从当前流程位置一直到烘干结束的剩余时间；在冲洗之前的阶段，按冲洗、沐浴、清洗、烘干四阶段总剩余时间上报；在单流程测试模式下，只上报当前测试阶段剩余时间。`current_stage_remaining_time_ms` 只表示当前小流程阶段自身剩余时间。配方时间来自当前活动配方，固定延时宏定义在 APP 固件 `auto_stages.h`，修改配方或宏后两个剩余时间会自动变化。

A5 ACK 示例：若设备发送 A5 的 `SEQ=0x13`，上位机应回复：

    55 AA F0 13 06 00 A5 00 00 00 00 00 CRC_L CRC_H

设备收到该 ACK 后只记录遥测已被上位机确认，不再对 ACK 回复任何帧。

无效传感器值应发送 `0xFFFF`，并将对应 valid bit 清零。温度采集模块断线返回 `0xFFFF`；APP 侧还会过滤明显超出物理范围的异常值。

当前 485 从站分配：1=增压泵变频器，2=冷热水比例调节阀，10=左风机，11=右风机，12=底部风机，13=顶部排风扇，14=左加热棒，15=右加热棒，16=底部加热棒，20=舱外温湿度/舱内氧气，21=四路水温采集模块，22=舱内温湿度，23=舱内臭氧。当前 21 号模块整体参与真实读取，CH3 管路出水口温度未接入时由 APP 使用固定值并按有效数据上报。

#### 12.1 【CMD=0x35/0xA6】查询输入和 GPIO 输出状态

`QUERY_IO_STATUS 0x35` 请求 Payload 为空。设备以相同 SEQ 返回
`IO_STATUS 0xA6`，Payload 布局如下：

除查询响应外，任一经过滤波的输入状态发生变化，或任一经过安全互锁后的
GPIO 实际输出状态发生变化时，设备都应立即主动发送 A6。状态无变化时每
5000 ms 补发一次 A6 心跳。主动帧使用设备独立 SEQ，查询响应必须回显请求
SEQ。

| **偏移** | **长度**                  | **类型** | **说明**                                         |
|----------|---------------------------|----------|--------------------------------------------------|
| 0        | 1                         | `uint8`  | `input_count`：输入点数量                        |
| 1        | 1                         | `uint8`  | `output_count`：GPIO 输出点数量                  |
| 2        | `(input_count+7)/8`       | 位图     | 输入位图，按 `AutoInputPoint` 枚举顺序排列       |
| 后续     | `(output_count+7)/8`      | 位图     | 实际输出位图，bit0 对应 output_id=1              |

位图采用低位优先：编号 
` 的逻辑状态位于 `bitmap[n/8]` 的
`bit(n%8)`；该位为1表示输入有效或输出打开，为0表示无效或关闭。最后一个
字节中超出计数范围的高位固定填0。当前19个输入占3字节、40个输出占5字节，
因此 A6 Payload 固定为10字节，而不是原先每点占1字节的61字节。

输出部分返回经过急停、门禁和光幕互锁后的实际 GPIO 状态。急停输入采用
失电安全逻辑：PB2 有正常回路信号时对应位为1，急停按下、断线或信号丢失
时对应位为0；设备安全逻辑会把后者解释为急停。

查询示例（SEQ=0）：

    主机发送：
    55 AA 35 00 00 00 6C 14
    设备返回（当前19输入、40输出）：
    55 AA A6 00 0A 00 13 28 IN_BITS[3] OUT_BITS[5] CRC_L CRC_H

接收端必须根据 `input_count`、`output_count` 计算两个位图的字节数，不能
把数量写死。

#### 12.2 【CMD=0x36】手动控制 RS485 执行器

`MANUAL_RS485_CONTROL 0x36` 仅在手动模式且急停正常时接受。请求 Payload 固定为 4 字节：

| **偏移** | **长度** | **类型** | **说明** |
|----------|----------|----------|----------|
| 0        | 2        | `uint16` | `station`：RS485 从站号，小端；当前允许 1、2、10~16 |
| 2        | 2        | `uint16` | `value`：站号 1 为增压泵压力，单位0.1kg，0~100；站号 2 为比例阀角度 0~90；站号 10~16 为功率百分比 0~100 |

站号定义：

| **站号** | **设备** | **0x36 value 含义** |
|----------|----------|---------------------|
| 1        | 增压泵变频器 | 压力设定值，单位0.1kg，15表示1.5kg；启动/停止由 `0x38` 控制 |
| 2        | 冷热水比例调节阀 | 角度 0~90；底层写寄存器 `0x0001`，值为 angle*100；在线状态按写入成功/失败判定，不参与只读巡检 |
| 10       | 左风机 | 功率百分比 0~100 |
| 11       | 右风机 | 功率百分比 0~100 |
| 12       | 底部风机 | 功率百分比 0~100 |
| 13       | 顶部排风扇 | 功率百分比 0~100 |
| 14       | 左加热棒 | 功率百分比 0~100 |
| 15       | 右加热棒 | 功率百分比 0~100 |
| 16       | 底部加热棒 | 功率百分比 0~100 |
| 20       | 舱外温湿度 + 舱内氧气传感器 | 只读传感器，禁止 0x36 控制 |
| 21       | 四路水温采集模块 | 只读传感器，禁止 0x36 控制 |
| 22       | 舱内温湿度传感器 | 只读传感器，禁止 0x36 控制 |
| 23       | 舱内臭氧传感器 | 只读传感器，禁止 0x36 控制 |

对 10~16 号可控硅执行器，上位机和自动流程统一使用百分比。STM32 底层按下式换算为整数电压，并写入可控硅保持寄存器 `0x0000`：

    voltage = round(percent * 240 / 100)

即 0%=0V、50%=120V、100%=240V。Modbus RTU 写入帧使用功能码 `0x06`，格式为“站号 06 00 00 电压高 电压低 CRC低 CRC高”。例如右风机 11 号站设置 100% 时，底层应发送：

    0B 06 00 00 00 F0 89 24

对 1 号增压泵，`value` 表示压力设定值，单位0.1kg，底层写变频器寄存器 `0x0000`，值直接等于 `value`。例如 1.0kg 对应 `value=10`，底层帧：

    01 06 00 00 00 0A 09 CD

例如 2.0kg 对应 `value=20`，底层帧：

    01 06 00 00 00 14 89 C5
对 2 号比例阀，`value` 表示角度，范围 0~90。STM32 底层将角度扩大 100 倍后写入比例阀保持寄存器 `0x0001`。比例阀不再用后台 `0x03` 读反馈寄存器作为在线判断，避免可写但不支持读反馈的阀体误报 `0x0809`；写角度成功视为通信恢复，写失败仍按命令失败上报 `0x0809`。

自动模式、急停触发、百分比/角度越界、站号越界或 RS485 队列繁忙时，设备返回 NACK；急停释放后不会自动恢复旧百分比、旧角度或旧压力。

#### 12.3 【CMD=0x37】切换执行器控制模式

`SET_ACTUATOR_MODE 0x37` 当前主要用于切换顶部排风扇的旧 GPIO/485 兼容控制来源；增压泵已经固定为 485 控制，不再受该模式开关影响。Payload 固定 2 字节：

| **偏移** | **长度** | **类型** | **说明** |
|----------|----------|----------|----------|
| 0        | 2        | `uint16` | `mode`：0=GPIO 执行器模式，1=485 执行器模式 |

当前默认 `mode=1`，即 485 执行器模式。增压泵已固定为 485 控制，不受该模式开关影响；切到 GPIO 模式时只会清零 13 号顶部排风扇功率，再返回 ACK；ACK 的 detail 为实际生效模式。

#### 12.4 【CMD=0x38】485 增压泵启动/停止

`BOOSTER_CONTROL 0x38` 用于 485 模式下启动或停止 1 号增压泵变频器。Payload 固定 2 字节：

| **偏移** | **长度** | **类型** | **说明** |
|----------|----------|----------|----------|
| 0        | 2        | `uint16` | `enabled`：0=停止，1=启动 |

底层 Modbus 示例：启动为 `01 06 20 00 00 01 43 CA`，停止为 `01 06 20 00 00 06 02 08`。压力设定值由 `CMD=0x36 station=1` 设置，单位0.1kg；未显式设定压力但启动泵时默认按5.0kg下发。配方中的冲洗/沐浴/清洗水压字段也按该压力值下发。自清洁药液喷洒使用配方 `self_clean_liquid_pressure_x10`，默认4.0kg；自清洁清水冲洗使用配方 `self_clean_rinse_pressure_x10`，默认6.0kg。

#### 12.5 【编译开关】空跑模式 `APP_DRY_RUN_ENABLE`

`APP_DRY_RUN_ENABLE` 是 APP 固件编译开关，不是上位机运行时 CMD。该宏为 `1` 时，APP 用于只连接 RS232 的流程联调：不访问真实 485 传感器和执行器，不驱动真实危险输出，遥测 `0xA5` 上传模拟传感器数据，门到位、液位、温度等流程条件由 APP 内部模拟通过。上位机仍按正式协议发送 `0x31/0x32/0x33/0x40~0x43` 等命令，便于验证自动流程、配方交互、A1/A3/A5 显示和日志记录。

空跑模式下参数读写和保存流程仍有效；上位机不能通过是否有真实 I/O 动作判断命令是否执行，只能以 ACK/NACK、A1 状态、A3 交互请求和 A5 遥测为准。正式设备联调和出厂固件应将该宏设为 `0` 后重新编译。


### 13. 快速/深度自检

#### 13.1 启动、暂停和停止

自检复用 `CMD=0x32 PROCESS_CONTROL`：

| `action` | `stage_id` | 说明 |
|---|---:|---|
| 9 | 0 | 启动快速自检 |
| 9 | 1 | 启动深度自检 |

设备仅在自动模式空闲、无急停、上下门关闭、双光幕未触发、液位组合有效且所需传感器有效时接受启动命令，成功返回 ACK，`detail=9`。自检运行期间，`action=2/3/4` 分别表示暂停、继续和安全停止。暂停会关闭泵、阀、风机和加热；继续时从当前检查项重新开始。

A1 状态中，自检使用 `process_type=5`、`stage_id=0x81`；自清洁固定使用 `stage_id=9`。

#### 13.2 自检结果 `0xA7 SELF_TEST_RESULT`

Payload 固定 14 字节：

| 偏移 | 长度 | 类型 | 说明 |
|---:|---:|---|---|
| 0 | 4 | `uint32` | `result_id` |
| 4 | 1 | `uint8` | `test_mode`：0快速，1深度 |
| 5 | 1 | `uint8` | `result_state`：0执行完成，1安全中止 |
| 6 | 4 | `uint32` | `tested_bitmap` |
| 10 | 4 | `uint32` | `passed_bitmap` |

设备每1000ms重发A7，直到上位机使用相同SEQ回复F0 ACK。ACK Payload为 `A7 00 result_id(uint32小端)`。

位图定义：

| bit | 检查项 |
|---:|---|
| 0~2 | 左、右、底部风机 |
| 3~5 | 左、右、底部加热管 |
| 6 | 增压泵 |
| 7 | 比例阀和OUT7自来水进水 |
| 8~11 | OUT9~12四路淋浴阀 |
| 12~15 | OUT20~23四路自清洁阀 |
| 16 | OUT24旁通阀 |
| 17 | OUT7+OUT39热水链路 |

快速模式检测三台风机485非零写入、三根加热管强制0%写入、增压泵、OUT9~12压力及比例阀进水。深度模式增加逐根温升、OUT20~24压力和OUT7+OUT39热水升温趋势。普通项目失败只反映在位图中；急停、门/光幕、液位矛盾、超温和超过4.0kg的超压会安全中止并发送A4。

`CMD=0x40/0x41` 使用 `group=2,index=0,protocol_version=1` 读写自检参数，data固定40字节：

| 偏移 | 长度 | 类型 | 默认值 | 说明 |
|---:|---:|---|---:|---|

### 14. 【实现说明，无单独 CMD】APP 侧实现状态

当前 APP 业务协议已在 `app_iap.c` 中接入主要业务 CMD：模式/流程控制、交互回复、GPIO 手动输出、IO 状态查询、485 手动控制、参数读写保存、A1/A3/A4/A5/A6/A7 上报等。当前协议文档按现有实现同步，后续如果继续调整站号、配方结构、A5 Payload 长度或新增业务 CMD，应同步更新本文档和上位机解析代码。

实现注意事项：

1.  参数协议仍要求按字段偏移解析，不能依赖不同编译器下 C 结构体裸内存布局。
2.  `CMD=0x36` 只写 485 目标值；1 号增压泵启动/停止必须使用 `CMD=0x38`。
3.  `CMD=0x37 mode=0` 表示切换到 GPIO 执行器模式，主要用于现场尚未安装 485 顶部排风扇时兼容旧硬件；增压泵固定走 485 控制。
4.  A5 中功率、角度、频率字段是 APP 最近一次485写入成功后的确认目标值，不是从站读回值。
5.  上电默认 MANUAL 手动模式，不会自动启动完整流程；完整流程仍需上位机先切 AUTO，再发送 `CMD=0x32 action=1`。
6.  单阶段测试（`0x32 action=5`）仅在手动模式接受，设备不代为切换模式；运行期间 `work_mode` 上报 3（单阶段测试模式），结束、主动停止或故障复位后自动回手动模式。
### 15. 【公共说明，适用于全部 CMD】兼容和版本管理

1.  `QUERY_INFO` 中协议版本目前为 1.1。业务协议落地时建议升级为 1.2，或在业务状态中增加独立版本字段。
2.  上位机必须先检查协议版本，再启用对应页面和命令。
3.  新字段优先追加在 Payload 尾部，不改变已有字段偏移。
4.  接收端以 LEN 判断可用字段，允许旧版本忽略尾部新增字段。
5.  保留未知 CMD 时返回 `BAD_CMD`，未知参数版本返回 `PARAM_VERSION_MISMATCH`。

# 第三部分：IAP 在线升级协议

## 1. IAP 升级流程总览

### 1. 升级系统角色

同一个 RS232 串口在不同阶段由不同程序接管：

| **阶段** | **MCU 运行程序**   | **串口职责**                                   |
|----------|--------------------|------------------------------------------------|
| 正常运行 | App                | 业务通信、设备信息查询、接收进入升级命令       |
| 切换阶段 | App -\> Bootloader | App 回复 ACK、写升级标志、软件复位             |
| 在线升级 | Bootloader         | 固件检查、擦除、分包接收、Flash 写入、整体校验 |
| 升级完成 | Bootloader -\> App | 回复成功、复位或跳转 App、恢复业务通信         |

现场在线升级只允许发送按 `APP_START_ADDR` 链接生成的完整 `App.bin`，禁止发送 Bootloader 或 `Factory_All.hex`。

### 2. 完整升级交互流程

#### 2.1 正常成功流程

    sequenceDiagram
        participant H as 上位机
        participant A as STM32 App
        participant B as STM32 Bootloader

        H->>A: QUERY_INFO，查询当前设备信息（SEQ=0）
        A-->>H: RSP_DEVICE_INFO，回复当前处于App模式（返回同一SEQ=0）
        Note over H: 检查产品型号、硬件版本、当前App版本、固件大小和CRC32

        H->>A: ENTER_UPGRADE，请求进入升级模式（SEQ=1，魔术值IAP1）
        A-->>H: RSP_ACK，确认允许升级（返回同一SEQ=1，状态OK）
        Note over A: 关闭泵、阀、风机和加热器等执行器
        Note over A: 写入升级标志，确认ACK发送完成，延时约100ms
        A->>B: MCU执行软件复位，Bootloader启动并接管串口
        Note over B: 初始化时钟、USART和升级状态
        B-->>H: RSP_BOOT_READY，主动通知Bootloader已准备好

        alt 上位机在1000ms内收到主动就绪帧
            Note over H: 确认已进入Bootloader，不再发送模式查询
        else 1000ms内没有收到主动就绪帧
            H->>B: QUERY_INFO，兜底查询Bootloader是否在线（SEQ=2）
            B-->>H: RSP_DEVICE_INFO，回复当前处于Bootloader模式（同一SEQ=2）
            Note over H: 查询超时才每500ms重试，最多3次，不是持续循环发送
        end

        H->>B: UPGRADE_START，发送目标型号、硬件范围、版本、大小和CRC32（SEQ=3）
        Note over B: 检查型号、硬件版本、大小和分包长度；产品允许降级
        Note over B: 清除App有效标志并擦除App区域
        B-->>H: RSP_ACK，开始升级成功，下一偏移为0（同一SEQ=3）

        loop 按App.bin顺序发送每个128字节数据块
            H->>B: UPGRADE_DATA，发送偏移、数据长度和固件数据（SEQ依次递增）
            Note over B: 检查帧CRC16、SEQ、偏移和地址，写入Flash
            B-->>H: RSP_ACK，返回下一包应发送的偏移（返回请求SEQ）
        end

        H->>B: UPGRADE_END，通知发送完成并携带总长度和整体CRC32
        Note over B: 检查接收长度、App向量表，并计算Flash整体CRC32
        B-->>H: RSP_ACK，固件整体校验成功并已标记App有效
        Note over B: 等待ACK完整发出，延时约100ms后自动软件复位
        B->>A: MCU软件复位，启动新App
        Note over A: 初始化时钟、USART和必要业务模块
        A-->>H: RSP_APP_READY，主动报告当前App版本、大小和CRC32
        Note over H: 将App报告的信息与本次升级文件信息进行比较
        alt 版本、大小、CRC32和目标型号均符合预期
            H->>A: APP_START_CONFIRM，通知版本核对成功
            A-->>H: RSP_ACK，确认已收到上位机核对结果
            Note over H: 本次升级流程完成
        else App报告的信息与升级目标不一致
            H->>A: APP_START_CONFIRM，通知版本核对失败并携带期望版本
            A-->>H: RSP_ACK，确认已收到核对失败结果
            Note over H: 本次升级标记为失败，显示实际版本并允许重新升级
        end

    sequenceDiagram

#### 3.2 QUERY_INFO / RSP_DEVICE_INFO

请求 Payload 为空。

响应 Payload：

| **偏移** | **字段**           | **类型** | **说明**                                  |
|----------|--------------------|----------|-------------------------------------------|
| 0        | `run_mode`         | u8       | `0=App`，`1=Bootloader`                   |
| 1        | `protocol_major`   | u8       | 本协议主版本，当前 `1`                    |
| 2        | `protocol_minor`   | u8       | 本协议次版本，当前 `1`                    |
| 3        | `app_valid`        | u8       | `0=无效`，`1=有效`                        |
| 4        | `target_id`        | u32      | 设备 ID，由芯片 96 位 UID 按标准 CRC32 压缩得到 |
| 8        | `hardware_version` | u16      | 硬件版本                                  |
| 10       | `boot_version`     | u32      | Bootloader 版本，例如 `0x00010200=V1.2.0` |
| 14       | `app_version`      | u32      | App 版本，无有效 App 时填 `0xFFFFFFFF`    |
| 18       | `app_start`        | u32      | App Flash 起始地址                        |
| 22       | `app_max_size`     | u32      | App 最大可用字节数                        |
| 26       | `max_chunk_size`   | u16      | Bootloader 支持的最大数据块               |

上位机升级前必须先查询并显示这些信息；`target_id` 由设备运行时上报，升级开始时应原样带回给 Bootloader，同时检查硬件版本范围和文件大小。

#### 3.3 ENTER_UPGRADE

请求 Payload：固定 4 字节 ASCII 魔术值 `IAP1`：

    49 41 50 31

App 仅在安全状态下接受该命令，例如 `IDLE`、`STOPPED`、`FAULT`、`DONE`。收到合法请求后：

1.  App 停止可控执行器并进入安全状态。
2.  App 发送 `RSP_ACK`，等待串口发送完成。
3.  App 保存升级标志 `IAP_ENTER_BOOT_MAGIC`。
4.  App 延时约 `100 ms`，调用 `NVIC_SystemReset()`。
5.  Bootloader 启动并接管同一 USART。
6.  Bootloader 完成时钟、串口和升级状态初始化后，主动发送 `RSP_BOOT_READY`。

若自动流程正在运行，App 返回 `ERR_BAD_STATE` 或 `ERR_BUSY`，不得复位。

#### 3.4 RSP_BOOT_READY

> **当前实现状态：Bootloader 尚未实现该主动帧**（`bootloader.c` 无 `0x92` 发送路径），上位机统一用 `QUERY_INFO` 兜底确认 Bootloader 在线即可；下文描述为设计目标，实现后再启用该兜底机制。

该帧由 Bootloader 启动后主动发送，不需要上位机先发查询命令。Bootloader 完成时钟、串口和升级状态初始化，确认已经可以接收命令后立即发送。若具体上位机在复位切换期间容易丢失首帧，可通过配置增加一个很短的发送延时，但不能在尚未准备好接收升级命令时提前发送。

`RSP_BOOT_READY` 只表示“Bootloader 已上线并可以接收升级命令”，不表示已经开始擦除或接收固件。上位机不需要回复该主动上报帧；确认固件信息无误后，仍由上位机发送 `UPGRADE_START`，因为固件版本、长度、CRC32 和目标型号都掌握在上位机一侧。

主动上报帧使用 Bootloader 自己的上报序号，设备每次复位后可从 `0x00` 开始。该 SEQ 不参与上位机请求序号的递增。

Payload：

| **偏移** | **字段**         | **类型** | **说明**                                                   |
|----------|------------------|----------|------------------------------------------------------------|
| 0        | `protocol_major` | u8       | 协议主版本，当前为 `1`                                     |
| 1        | `protocol_minor` | u8       | 协议次版本，当前为 `1`                                     |
| 2        | `app_valid`      | u8       | 当前 App 是否有效                                          |
| 3        | `boot_reason`    | u8       | `1=App请求升级`，`2=App无效`，`3=升级失败后重启`，`0=其他` |
| 4        | `app_start`      | u32      | App 起始地址                                               |
| 8        | `app_max_size`   | u32      | App 最大允许长度                                           |
| 12       | `max_chunk_size` | u16      | 最大固件分包数据长度                                       |

上位机收到该帧后即可确认 MCU 已从 App 切换到 Bootloader。为防止该主动帧因复位切换或链路干扰丢失，上位机采用以下兜底机制：

1.  收到 App 的 ENTER_UPGRADE 成功 ACK 后开始监听 Bootloader 就绪帧。
2.  最多等待 `1000 ms`；期间上位机不连续发送查询命令。
3.  `1000 ms` 内未收到 `RSP_BOOT_READY`，再发送一次 `QUERY_INFO`。
4.  QUERY_INFO 超时后每 `500 ms` 重试一次，最多重试 3 次。
5.  收到 `RSP_BOOT_READY` 或 `RSP_DEVICE_INFO(mode=Bootloader)` 后停止查询并进入升级流程。
6.  仍无响应时判定模式切换失败，不发送 START/DATA。

#### 3.5 RSP_APP_READY / APP_START_CONFIRM

App 每次启动并完成时钟、串口及必要业务初始化后，主动发送一次 `RSP_APP_READY`。这一步不需要上位机先发送 QUERY_INFO。

`RSP_APP_READY` Payload：

| **偏移** | **字段**           | **类型** | **说明**                                                   |
|----------|--------------------|----------|------------------------------------------------------------|
| 0        | `protocol_major`   | u8       | 协议主版本                                                 |
| 1        | `protocol_minor`   | u8       | 协议次版本                                                 |
| 2        | `reset_reason`     | u8       | `1=上电`，`2=Bootloader升级后启动`，`3=软件复位`，`0=其他` |
| 3        | `reserved`         | u8       | 固定为 0                                                   |
| 4        | `target_id`        | u32      | 设备 ID，由芯片 96 位 UID 按标准 CRC32 压缩得到             |
| 8        | `hardware_version` | u16      | 当前硬件版本                                               |
| 10       | `app_version`      | u32      | 当前运行 App 的版本号                                      |
| 14       | `app_size`         | u32      | 当前 App 固件大小                                          |
| 18       | `app_crc32`        | u32      | Bootloader 校验并记录的固件 CRC32                          |

App 只知道“我当前运行的版本是什么”，不知道上位机本次期望升级到哪个版本。因此，版本是否符合预期由上位机判断：

1.  上位机收到 `RSP_APP_READY`。
2.  比较 `target_id` 是否等于本次升级前设备上报的 ID，同时核对 `app_version`、`app_size` 和 `app_crc32`。
3.  比较一致时，发送 `APP_START_CONFIRM(result=0)`。
4.  比较不一致时，发送 `APP_START_CONFIRM(result=1)`，上位机将本次升级标记为失败并提示实际版本。
5.  App 收到确认命令后回复通用 `RSP_ACK`，可将结果记录到运行日志，但不能把上位机确认作为 App 是否允许运行的条件。

`APP_START_CONFIRM` Payload：

| **偏移** | **字段**           | **类型** | **说明**                                   |
|----------|--------------------|----------|--------------------------------------------|
| 0        | `result`           | u8       | `0=版本及固件信息符合预期`，`1=不符合预期` |
| 1        | `reserved`         | u8       | 固定为 0                                   |
| 2        | `expected_version` | u32      | 上位机期望的 App 版本                      |
| 6        | `expected_crc32`   | u32      | 上位机期望的 App CRC32                     |

如果上位机没有收到 `RSP_APP_READY`，等待 `1000 ms` 后发送 QUERY_INFO 进行兜底查询，每 `500 ms` 重试一次，最多 3 次。

> `APP_START_CONFIRM` 是升级流程的业务闭环确认，不是固件有效性判定。固件是否完整、是否允许启动，必须已经由 Bootloader 的 CRC32、向量表和有效标志检查完成。当前为单 App 分区方案，版本不一致时也无法自动回滚，只能由上位机重新发起升级。

#### 3.6 UPGRADE_START

请求 Payload 固定 22 字节：

| **偏移** | **字段**     | **类型** | **说明**                           |
|----------|--------------|----------|------------------------------------|
| 0        | `target_id`  | u32      | 必须等于升级前 `QUERY_INFO` 读到的设备 ID |
| 4        | `hw_min`     | u16      | 支持的最低硬件版本                 |
| 6        | `hw_max`     | u16      | 支持的最高硬件版本                 |
| 8        | `fw_version` | u32      | 新 App 版本                        |
| 12       | `fw_size`    | u32      | `App.bin` 精确字节数               |
| 16       | `fw_crc32`   | u32      | 整个 `App.bin` 的 CRC32            |
| 20       | `chunk_size` | u16      | 本次会话采用的数据块大小，推荐 128 |

产品允许固件降级，因此 Bootloader 记录并返回版本号，但不根据新旧版本大小关系拒绝升级。Bootloader 必须先检查目标型号、硬件版本、固件大小和 chunk，再擦除 App 区。擦除完成后才发送 ACK。ACK 中 
ext_offset=0`。

执行 START 后立即将 App 标记为无效。任何掉电、取消或失败都不能再跳转到被部分擦写的 App。

#### 3.7 UPGRADE_DATA

请求 Payload：

| **偏移** | **字段**   | **类型** | **说明**                             |
|----------|------------|----------|--------------------------------------|
| 0        | `offset`   | u32      | 相对于 `APP_START_ADDR` 的偏移       |
| 4        | `data_len` | u16      | 本包固件数据长度                     |
| 6        | `data`     | byte\[\] | `App.bin[offset..offset+data_len-1]` |

约束：

1.  `offset` 必须等于 MCU 当前 
ext_offset`。
2.  除最后一包外，`data_len` 必须等于 START 中的 `chunk_size`。
3.  `offset + data_len` 不得大于 `fw_size`。
4.  Flash 写地址为 `APP_START_ADDR + offset`，不得进入 Bootloader 或元数据区。
5.  建议 chunk 为 128 字节，且 offset 保持 8 字节对齐。
6.  最后一包不足 Flash 双字时，MCU 可在写 Flash 时用 `0xFF` 补齐，但 
ext_offset` 和 CRC32 只计算实际数据长度。
7.  MCU 写入并可选读回校验成功后才回复 ACK，ACK 的 
ext_offset=offset+data_len`。

#### 3.8 QUERY_PROGRESS / RSP_PROGRESS

> **当前实现状态：Bootloader 尚未实现 `QUERY_PROGRESS`（0x24）/`RSP_PROGRESS`（0x91）**（`bootloader.c` 无 `0x24` 分支）。当前固件升级中断/掉电后只能重新 `START` 从 0 开始，上位机不依赖本命令；下文为设计目标，实现后再启用断点续传。

请求 Payload 为空。响应 Payload：

| **偏移** | **字段**        | **类型** | **说明**                   |
|----------|-----------------|----------|----------------------------|
| 0        | `upgrade_state` | u8       | 见 IAP 第 4 节（状态机）                  |
| 1        | `last_error`    | u8       | 最近错误码                 |
| 2        | `expected_seq`  | u8       | 下一请求期望序号           |
| 3        | `app_valid`     | u8       | 当前 App 是否有效          |
| 4        | `fw_size`       | u32      | 当前会话固件大小           |
| 8        | 
ext_offset`   | u32      | 下一包应发送偏移           |
| 12       | `running_crc32` | u32      | 可选运行 CRC；未实现时填 0 |

串口短暂中断但 MCU 未复位时，上位机可查询进度并从 
ext_offset` 继续。MCU 掉电复位后不要求保存分包进度，上位机应重新发送 START 并从 0 开始。

#### 3.9 UPGRADE_END

请求 Payload 固定 8 字节：

| **偏移** | **字段**   | **类型** |
|----------|------------|----------|
| 0        | `fw_size`  | u32      |
| 4        | `fw_crc32` | u32      |

Bootloader 依次执行：

1.  检查 
ext_offset == fw_size`。
2.  检查 END 参数与 START 参数一致。
3.  检查 App 初始 MSP 位于合法 SRAM 范围。
4.  检查 App Reset_Handler 位于 App Flash 范围且 Thumb 位有效。
5.  对 Flash 中 `fw_size` 字节计算 CRC32。
6.  CRC32 一致后写入固件大小、版本、CRC 和 App 有效标志。
7.  最后发送 ACK；校验失败发送 NACK，并保持在 Bootloader。
8.  ACK 完整发送后等待 UART TC，延时约 `100 ms` 并自动软件复位。
9.  MCU 重新进入 Bootloader，确认 App 有效后自动跳转新 App。

#### 3.10 UPGRADE_ABORT

Payload 为空。

| **情况**              | **Bootloader 行为**                             |
|-----------------------|-------------------------------------------------|
| 尚未执行 START        | 清除进入升级标志；若旧 App 有效，可允许 RUN_APP |
| 已执行 START/擦除 App | 终止会话并保持 App 无效，继续停留 Bootloader    |

#### 3.11 RUN_APP

Payload 为空。Bootloader 仅在 App 有效时回复 ACK，然后优先执行软件复位，由正常启动路径进入 App。若 App 无效，返回 `ERR_APP_INVALID`。该命令主要用于取消升级后启动仍有效的旧 App或调试场景；正常升级成功后由 Bootloader 自动复位，不需要上位机再发送 RUN_APP。

### 4. Bootloader 升级状态机

| **状态**       | **数值** | **允许命令**                             | **说明**                                |
|----------------|----------|------------------------------------------|-----------------------------------------|
| `BL_IDLE`      | `0`      | QUERY_INFO、START、ABORT、RUN_APP        | 等待升级；App 无效时禁止 RUN_APP        |
| `BL_ERASING`   | `1`      | QUERY_INFO、QUERY_PROGRESS               | 正在擦除，其他命令返回 BUSY             |
| `BL_RECEIVING` | `2`      | DATA、END、ABORT、QUERY_PROGRESS         | 接收和写入数据                          |
| `BL_VERIFYING` | `3`      | QUERY_INFO、QUERY_PROGRESS               | 正在计算整体 CRC                        |
| `BL_COMPLETE`  | `4`      | QUERY_INFO、RUN_APP                      | 固件有效；正常流程在 END ACK 后自动复位 |
| `BL_FAILED`    | `5`      | QUERY_INFO、START、ABORT、QUERY_PROGRESS | 升级失败，可重新 START                  |

    stateDiagram-v2
        [*] --> BL_IDLE
        BL_IDLE --> BL_ERASING: 收到合法的开始升级命令 UPGRADE_START
        BL_ERASING --> BL_RECEIVING: App区擦除成功并回复ACK
        BL_ERASING --> BL_FAILED: App区擦除失败并回复NACK
        BL_RECEIVING --> BL_RECEIVING: 收到固件数据 UPGRADE_DATA，写入并回复ACK
        BL_RECEIVING --> BL_VERIFYING: 收到结束升级命令 UPGRADE_END
        BL_RECEIVING --> BL_FAILED: 收到取消命令、会话超时或Flash写入失败
        BL_VERIFYING --> BL_COMPLETE: CRC32、向量表校验通过
        BL_VERIFYING --> BL_FAILED: 校验失败
        BL_COMPLETE --> [*]: END的ACK发送完成后自动复位，或收到RUN_APP
        BL_FAILED --> BL_ERASING: 收到新的开始升级命令，重新完整升级

### 5. 分包、超时和重试参数

| **项目**                | **推荐值** | **说明**                             |
|-------------------------|------------|--------------------------------------|
| 最大 Payload            | `256 B`    | MCU 接收缓冲区至少为 256 字节        |
| 固件 data_len           | `128 B`    | 现场干扰和效率之间的默认折中         |
| 普通命令超时            | `500 ms`   | QUERY、ENTER、ABORT、RUN_APP         |
| DATA ACK 超时           | `1000 ms`  | 从整帧发送完成后开始计时             |
| START 超时              | `15000 ms` | 包含 Flash 擦除时间                  |
| END 超时                | `10000 ms` | 包含全固件 CRC32 校验时间            |
| 单帧最大重试            | `3 次`     | 每次使用原 CMD/SEQ/Payload           |
| Bootloader 会话空闲超时 | `30 s`     | 超时不跳转无效 App，仍可等待新 START |
| App 切换等待            | `5 s`      | ENTER ACK 后轮询 Bootloader 的总时限 |

重试用尽后，上位机应保存日志并执行一次 `QUERY_PROGRESS`。如果 Bootloader 在线且进度明确，可继续；状态不确定或 MCU 已复位时，重新发送 START 并从头升级。

### 6. 报文示例

以下示例均使用小端格式和 CRC16/CCITT-FALSE。`CRC_L CRC_H` 的具体值应由组包程序自动计算，不允许手工固定。

#### 6.1 查询设备信息

上位机发送，`SEQ=0x00`：

    55 AA 10 00 00 00 67 9F

CRC 输入为：

    10 00 00 00

#### 6.2 请求 App 进入升级

上位机发送，Payload 为 ASCII `IAP1`：

    55 AA 11 01 04 00 49 41 50 31 22 6A

App 成功响应，`request_cmd=0x11, status=0, next_offset=0`：

    55 AA F0 01 06 00 11 00 00 00 00 00 40 EE

#### 6.3 Bootloader 主动通知已准备好

假设 Bootloader 启动原因为 App 请求升级，当前 App 有效，App 起始地址为 `0x08010000`，App 最大空间为 `0x0006F800`，最大分包为 128 字节。

Bootloader 初始化完成后主动发送：

    55 AA 92 00 0E 00
    01 01 01 01
    00 00 01 08
    00 F8 06 00
    80 00
    0C 41

字段解释：

    92          = RSP_BOOT_READY，Bootloader就绪通知
    00          = Bootloader主动上报序号
    0E 00       = Payload长度14字节
    01 01       = 协议版本V1.1
    01          = 当前App有效
    01          = 启动原因为App请求升级
    00 00 01 08 = App起始地址0x08010000
    00 F8 06 00 = App最大空间0x0006F800
    80 00       = 最大分包128字节
    0C 41       = 帧CRC16，小端发送

上位机收到这帧后，不需要继续发送 QUERY_INFO，可以直接发送 UPGRADE_START。只有在规定时间内没有收到该帧，才使用 QUERY_INFO 进行兜底确认。

#### 6.4 开始升级

假设：

    target_id  = 0x0000474E
    hw_min     = 0x0001
    hw_max     = 0x0002
    fw_version = 0x00010203 (V1.2.3)
    fw_size    = 0x00000400 (1024 字节，仅用于示例)
    fw_crc32   = 0x12345678 (仅用于示例)
    chunk_size = 0x0080 (128 字节)

上位机发送：

    55 AA 20 02 16 00
    4E 47 00 00 01 00 02 00 03 02 01 00
    00 04 00 00 78 56 34 12 80 00
    78 0A

Bootloader 擦除完成后回复：

    55 AA F0 02 06 00 20 00 00 00 00 00 28 A9

#### 6.5 发送一包固件数据

为便于阅读，本例只发送 16 字节 `00~0F`；正式升级建议每包 128 字节。

    offset   = 0x00000000
    data_len = 0x0010
    data     = 00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F

上位机发送：

    55 AA 21 03 16 00
    00 00 00 00 10 00
    00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
    DC CD

Bootloader 成功写入后回复 
ext_offset=0x10`：

    55 AA F0 03 06 00 21 00 10 00 00 00 0C 1C

#### 6.6 结束升级

上位机发送：

    55 AA 22 04 08 00 00 04 00 00 78 56 34 12 83 E6

整体校验成功后 Bootloader 回复：

    55 AA F0 04 06 00 22 00 00 04 00 00 20 A4

### 7. 上位机程序实现要求

上位机升级模块至少包含以下逻辑：

1.  串口接收线程维护字节流缓冲区，通过 `55 AA` 搜索帧头，并按 LEN 提取完整帧。
2.  遇到非法 LEN 或 CRC16 错误时丢弃当前候选帧，从下一个可能帧头重新同步。
3.  升级发送采用 stop-and-wait：任何时刻只允许一个未确认请求。
4.  仅在收到同 SEQ 的有效响应后推进发送状态；其他 SEQ 的响应记录后忽略。
5.  固件文件打开后固定其大小、CRC32 和版本信息，升级过程中禁止文件被替换。
6.  每个 DATA ACK 后按 
ext_offset / fw_size` 更新进度，不按已发送字节盲目更新。
7.  记录时间、串口号、设备信息、旧/新版本、固件 SHA-256（建议）、CRC32、包序号、重试次数和最终错误。
8.  END 成功不等于最终完成；必须等待新 App 主动发送 `RSP_APP_READY`，并核对目标型号、版本、大小和 CRC32。未收到主动帧时才使用 QUERY_INFO 兜底查询。
9.  核对完成后发送 `APP_START_CONFIRM`，并以其 ACK 作为升级业务流程闭环。
10. 用户取消升级时发送 ABORT，并明确提示旧 App 是否仍然有效。

上位机核心状态建议：

    DISCONNECTED -> APP_ONLINE -> ENTERING_BOOT -> BOOT_ONLINE
                 -> STARTING -> SENDING -> VERIFYING -> REBOOTING
                 -> COMPLETE / FAILED / CANCELLED

### 8. STM32 App 实现要求

1.  App 支持 QUERY_INFO、ENTER_UPGRADE 和 APP_START_CONFIRM。
2.  ENTER_UPGRADE 必须验证魔术值和当前业务安全状态。
3.  ACK 必须在写升级标志和复位之前完整发出，并确认 UART TX 完成。
4.  进入升级前关闭泵、阀、风机、加热器等执行器。
5.  升级标志必须位于复位后仍可读取的位置，且不能因普通业务参数写入被误改。
6.  App 链接地址和 VTOR 必须设置为 `APP_START_ADDR`，当前默认 `0x08010000`。
7.  App 提供固定的目标型号、硬件版本和 App 版本，供 QUERY_INFO 返回。
8.  App 启动并完成必要初始化后主动发送 `RSP_APP_READY`，报告自身版本、大小和 CRC32；收到 APP_START_CONFIRM 后回复 ACK。

### 9. STM32 Bootloader 实现要求

1.  Bootloader 只允许擦写 `[APP_START_ADDR, METADATA_PAGE_ADDR)`。
2.  START 参数全部校验通过后才能擦除；擦除前使 App 有效标志失效。
3.  每个 DATA 包先校验帧 CRC16、SEQ、offset、长度和地址，再写 Flash。
4.  DATA 成功响应应在 Flash 写入完成后发送，必要时增加写后读回比较。
5.  对重复包必须幂等处理，不能因 ACK 丢失重复编程同一 Flash 地址。
6.  Bootloader 不得因接收超时跳转到无效 App。
7.  App 有效标志必须最后写入；只有大小、向量表、Reset_Handler 和 CRC32 均通过后才可写入。
8.  跳转 App 前关闭中断、停止 SysTick、反初始化外设、设置 VTOR/MSP，然后跳转 Reset_Handler；推荐软件复位后由统一启动路径进入 App。
9.  元数据建议保存：magic、状态、target_id、fw_version、fw_size、fw_crc32、app_valid 和元数据自身 CRC。

### 10. 与仓库当前代码的差异

当前代码可作为功能原型，但尚未满足需求书 V1.1 的全部通信要求：

| **项目**     | **当前代码**             | **V1.1 目标**                        |
|--------------|--------------------------|--------------------------------------|
| 帧长度       | 1 字节，表示 CMD+Payload | 2 字节，表示 Payload                 |
| 帧校验       | 8 位累加和               | CRC16/CCITT-FALSE                    |
| SEQ          | 无                       | 每个请求必须有 SEQ                   |
| 重复包处理   | 无                       | 缓存响应，重复包幂等                 |
| 固件描述     | size + CRC32             | 增加型号、硬件范围、版本和 chunk     |
| 设备信息查询 | IAP 仅返回地址和进度     | 返回模式、目标型号、软硬件版本和能力 |
| 乱序检测     | 主要依赖 offset          | SEQ + offset 双重检查                |
| 恢复机制     | 无明确上位机策略         | QUERY_PROGRESS + next_offset         |

因此，上位机若按本文 V1.1 开发，STM32 的 `HostCommTask.c/.h`、`IapBoot.c/.h` 和配置文件也必须按同一版本调整。联调时应首先用固定测试向量验证 CRC16、CRC32、大小端和示例帧，再进行真实 Flash 升级。

### 11. 联调与验收用例

至少验证以下场景：

1.  正常升级并在 App 重启后查询到新版本。
2.  错误帧头、非法 LEN、错误 CRC16 被拒绝且后续帧可重新同步。
3.  DATA ACK 丢失后相同包重发，Flash 不重复写且进度正确。
4.  跳包、乱序包、相同 SEQ 不同内容均返回明确 NACK。
5.  错误 target_id、硬件版本不匹配和固件超大均在擦除前被拒绝；target_id 应使用设备查询返回值，高版本升级到低版本应允许执行。
6.  固件数据篡改导致 END CRC32 失败，App 不被标记有效。
7.  START 前取消可返回旧 App；START 擦除后取消不能进入旧 App。
8.  升级各阶段断电，重新上电后 Bootloader 不跳转无效 App，并可重新完整升级。
9.  最后一包非 8 字节倍数时，实际长度、Flash 补齐和 CRC32 均正确。
10. SEQ 从 `0xFF` 回绕到 `0x00` 后仍能正常升级。
11. 115200 波特率、目标线长和现场干扰条件下连续升级至少 100 次无失败。
12. 上位机日志能够定位最后成功 offset、错误码、重试次数和最终结果。

## 4. 常见问题

### Q1：业务协议和 IAP 协议是不是同一套协议？

不是同一类业务，但共用基础帧格式和公共响应。业务协议运行在 App，用于设备控制；IAP 协议跨 App 和 Bootloader，用于在线升级。

### Q2：为什么 ACK 的第三个字段有时叫 detail，有时叫 next_offset？

两者字段位置和长度相同，都是 `uint32`。在 APP 业务协议中它表示业务细节，例如模式、动作结果、request_id 或 revision；在 IAP 升级协议中它表示 Bootloader 下一包期望偏移 
ext_offset`。

### Q3：完整自动流程怎么启动？

当前 APP 上电默认进入 MANUAL 手动模式，不会自行启动完整流程；上位机需要先发送 `CMD=0x31 SET_WORK_MODE(AUTO)` 切到自动模式空闲层，再发送 `CMD=0x32 action=1` 启动完整自动流程。

### Q4：`PROCESS_CONTROL action=7` 是不是 MCU 重启？

不是。它表示清除故障锁存和复位流程状态，不是整机软件重启。如果需要进入 Bootloader，应使用 IAP 的 `CMD=0x11 ENTER_UPGRADE`。

### Q5：上位机为什么不能只按 SEQ 去重？

主动上报使用设备独立 SEQ，且设备可能重复上报同一个 `request_id` 或 `event_id`。因此流程交互必须按 `request_id` 去重，故障事件必须按 `event_id` 去重。

### Q6：最后一包固件不足 Flash 写入对齐怎么办？

Bootloader 可以在写 Flash 时用 `0xFF` 补齐，但 
ext_offset` 和 CRC32 只按实际固件数据长度计算，不能把补齐字节计入固件 CRC32。

### Q7：IAP 升级过程中掉电后怎么办？

如果 START 已执行，App 有效标志已清除。重新上电后 Bootloader 不得跳转无效 App，上位机应重新发送 START 并从 offset=0 开始完整升级。
